## Сознательно не исправлено (9)

Ни одно из них не дешёвое. Каждому нужна либо новая версия формата обмена, либо
двусторонняя смена протокола, либо миграция, у которой радиус поражения больше
самого бага.

### Шифрование

**1. Обёртка секторного ключа ничего не аутентифицирует (нет AAD)** — `client/src/lib/chat-logic.ts`
Старый обёрнутый ключ можно переиграть как текущую эпоху. Починка — привязать
канонический заголовок как `additionalData` у AES-GCM, а это меняет то, что
аутентифицирует *каждая* обёртка. Значит, нужен payload `v:3` рядом с `v:2`,
причём `v:2` должен продолжать приниматься, пока все развёрнутые клиенты не
провернут ротацию. Односторонняя правка отрезает каждую существующую группу от её
собственной истории.

**2. Две сессии могут разойтись в ключах на одной эпохе** — `client/src/hooks/use-group-key-distribution.ts`
Для сходимости нужен серверный compare-and-swap по `chats.key_epoch`, чтобы
ротация второй сессии на той же эпохе отклонялась. Это отдельный роут плюс вопрос
схемы; клиентская половина сама по себе безопасной ситуацию не делает. Со стороны
чтения частично смягчено кольцом эпох.

**3. У секторных МЕДИА один ключ без кольца эпох** — `client/src/hooks/use-chat-aes-key.ts`
Хук возвращает один `CryptoKey`, который уходит в `decryptBinary` в трёх местах.
Вернуть кольцо — значит поменять все три разом; частичная правка будет мёртвым
кодом.

**4. X3DH-prekey'и детерминированно выводятся из статического ключа хранилища** — `client/src/lib/ratchet/identity-from-vault.ts`
Подтверждено: утечка хранилища задним числом восстанавливает X3DH-секрет каждой
архивной сессии, то есть одноразовые prekey'и не дают никакой forward secrecy.
Сделать их случайными — значит их надо хранить и перепубликовывать, а это
одновременно задевает справочник ключей, загрузку бандла и формат бэкапа
хранилища.

**5. Кадры relay-звонка идут без AAD, без порядкового номера и на статическом ключе** — `client/src/hooks/use-webrtc.ts`
Привязка AAD требует новых параметров `additionalData` у общих
`encryptBytes`/`decryptBytes` в `lib/crypto.ts` — их используют и веерная рассылка
сообщений, и групповая обёртка — плюс согласованных правок в
`group-call-manager`. Смена протокола обмена сразу в трёх подсистемах.

**6. Публикация публичного ECDH-ключа не требует доказательства разблокировки хранилища** — `server/src/routes/users.ts`
`patchMyEcdhPublicKey` вызывается при каждом входе и каждой разблокировке
хранилища без всякого доказательства, так что голая угнанная сессия может
перенаправить веерное шифрование пиров на себя. Починка двусторонняя: клиент
должен подписывать серверный nonce ECDSA-ключом из связки. Включить проверку
только на сервере — значит отрезать всех текущих клиентов.

### Бэкенд / инфраструктура

**7. Горячий запрос по `messages.media_path` без индекса** — `server/src/routes/storage.ts`
`messages_media_path_idx` построен по `created_at`, а `media_path` фигурирует
только в частичном предикате; `messages_chat_media_idx` начинается с `chat_id`,
который этот запрос не ограничивает. Нужна новая миграция плюс объявление индекса
в `schema.ts`. На текущих объёмах безвредно.

**8. У `clearBackupPending()` нет ни одного вызова в проде** — `client/src/lib/backup-reminder.ts`
Баннер «у вас всё ещё нет способа вернуться в аккаунт» не сбрасывается двумя
событиями, которые обязаны его сбрасывать. Места вызова — в
`settings-devices-panel.tsx` и на успешном пути записи фразы восстановления, то
есть вне файлов той группы, что владела находкой. Мелочь, но сделать стоит
следующей.

**9. LiveKit :7880 слушает открытым текстом на всех интерфейсах** — `docker/livekit/livekit.yaml`
Предложенная починка (привязать к 127.0.0.1) положила бы групповые звонки: Caddy
живёт отдельным контейнером в `~/infra/caddy` и ходит к SFU через шлюз
docker-моста, а не через loopback. Правильный контроль здесь — файрвол хоста, и
`ufw` с default-deny его уже обеспечивает; чек-лист теперь записан прямо рядом с
сервисом в `docker-compose.prod.yml`.

## Опровергнуто при ревью фиксов

Сообщено, но не подтвердилось при разборе кода. Записано, чтобы не поднимать
заново.

| Находка | Почему отклонено |
|---------|------------------|
| Записи кольца разворачиваются без привязки к владельцу | Любая запись попадает в кольцо только после проверки привязки к владельцу на записи; `buildSectorFrame` — единственный писатель |
| `recordFailure` через EVAL против `checkLockout` через GET/TTL | Оба пути деградируют одинаково; скриптинг на развёрнутом Redis доступен |
| `skipOnError` у Redis-лимитера открывает проход | Лимитер падает обратно на in-memory store, а не пропускает проверку |
| Удаление личного чата навсегда вешает вложения на квоту | Строки квоты уходят вместе с чатом |
| Blob-URL стикера отзывается между resolve и commit | URL удерживается до следующего resolve того же стикера |

Ещё четыре были опровергнуты только потому, что их уже починили раньше в этой же
сессии, и проверяющие читали уже исправленный код: проверка Origin от CSWSH, ключ
хранилища, переживающий выход, бан/удаление создателя админом и `env_file` у
coturn.
