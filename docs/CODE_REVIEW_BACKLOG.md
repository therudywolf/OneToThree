## Что закрыто в раунде 3

**Утечка конфиденциальности переписки**

- **Публикация ECDH-ключа теперь требует доказательства разблокировки хранилища**
  (`b4b0321`). `PATCH /users/me` принимал новый публичный ключ по одной лишь куке
  сессии — а это ключ, которым шифруют все пиры. Угнанная сессия молча
  перенаправляла входящие сообщения жертвы атакующему, без пароля хранилища.
  Теперь клиент подписывает одноразовый серверный nonce ECDSA-ключом из связки,
  который существует только после разблокировки. У `verifyVaultProof` появился
  `scope`, чтобы nonce, выданный для экрана восстановления, нельзя было потратить
  на подмену ключа.

- **X3DH-prekey'и снова случайные** (`df07ef9`). Они были HKDF от скаляра
  хранилища, то есть одноразовые ключи были детерминированной функцией
  долговременного секрета — утечка хранилища задним числом вскрывала X3DH-секрет
  каждой сессии. Теперь генерируются `crypto.getRandomValues`, приватные половины
  лежат в отдельном IndexedDB-хранилище, публикуются только публичные.
  Identity-ключ намеренно остался выводимым из хранилища: он и должен быть
  долговременным, его удостоверяет safety number.

**Потеря данных**

- **Кольцо эпох для медиа** (`d1bd36f`). У сообщений кольцо было с #32, у медиа —
  нет. Любая ротация ключа (то есть любое изменение состава группы) навсегда
  закрывала доступ ко всем ранее загруженным файлам. Кольцо теперь регистрируется
  при сборке крипто-контекста и используется как запасной путь расшифровки.

- **CAS по эпохе на сервере** (`b9ad287`). Две сессии владельца могли
  одновременно выпустить разные ключи под одним номером эпохи — группа
  раскалывалась на два ключа без возможности самолечения. Теперь инкремент эпохи
  условный (`WHERE key_epoch = ?`), проигравший получает 409 и прекращает
  ротацию, а не рассыпает второй ключ по составу.

**Укрепление**

- **v3-обёртка секторного ключа** (`d1bd36f`). AAD связывает `чат | эпоха |
  ключ создателя | участник`, и читатель собирает AAD из СВОЕГО контекста, а не
  из полезной нагрузки. Переставить эпоху, подсунуть блоб в другой чат или
  другому участнику больше нельзя — расшифровка падает. Ключи момента создания
  группы намеренно остаются v2: чата ещё не существует, привязывать не к чему.

- **Кадры relay-звонка** (`7d89b6c`). Ключ на пару собеседников был статическим
  навсегда, кадры шли без AAD и без счётчика. Теперь: nonce на звонок в
  `relay_offer`/`relay_answer` подмешивается в HKDF info (свой ключ на каждый
  звонок), AAD связывает направление и позицию, счётчик строго возрастает.

- **LiveKit :7880 закрыт** (`6e4c082`). Конфиг утверждал, что порт закрыт
  файрволом — **проба из интернета отвечала 200**. Плейнтекстовый HTTP/WS с
  room-JWT и Twirp-поверхностью в обход Caddy/Anubis/CrowdSec. Привязка к
  loopback положила бы звонки (Caddy — отдельный контейнер, ходит через шлюз
  docker-моста), поэтому entrypoint определяет шлюз в рантайме и биндится к
  нему. Проверено на живом деплое: публичный порт недоступен, через Caddy 200,
  медиапорт 7881 открыт.

- **Индекс `messages.media_path`** и **вызовы `clearBackupPending()`**
  (`6e4c082`) — три горячих запроса перестали сканировать таблицу; баннер
  «нет способа вернуться в аккаунт» теперь гаснет при сохранении файла ключа или
  записи фразы восстановления.

## Что сломано намеренно

Переход на v3 несовместим со старыми данными:

- групповые ключи в обёртке v2 при первой же ротации заменяются на v3;
- ранее опубликованные prekey'и невалидны — сессии переустанавливаются;
- клиенты без обновления перестают работать до перезагрузки.

На 5 тестовых аккаунтах это никого не задело.

## Проверка

Все девять покрыты регресс-тестами: доказательство при публикации ECDH (5
случаев), случайность prekey'ев (4), CAS по эпохе (серверный, воспроизводит
гонку), привязка v3 (6), кадры relay (6). Тесты фиксируют СВОЙСТВО, а не
реализацию: возврат к `deriveOtpPrivKey(dRoot, id)` или к обёртке без AAD их
роняет.

Итог: **239/239 сервер, 368/368 клиент**, `tsc` + `eslint` чисто с обеих сторон,
паритет локалей 1122/1122, серверный прогон завершается кодом 0 без
необработанных ошибок.

## Опровергнуто при ревью раунда 2

Сообщено, но не подтвердилось при разборе кода. Записано, чтобы не поднимать
заново.

| Находка | Почему отклонено |
|---------|------------------|
| Записи кольца разворачиваются без привязки к владельцу | Запись попадает в кольцо только после проверки привязки; `buildSectorFrame` — единственный писатель |
| `recordFailure` через EVAL против `checkLockout` через GET/TTL | Оба пути деградируют одинаково; скриптинг на развёрнутом Redis доступен |
| `skipOnError` у Redis-лимитера открывает проход | Лимитер падает обратно на in-memory store, а не пропускает проверку |
| Удаление личного чата навсегда вешает вложения на квоту | Строки квоты уходят вместе с чатом |
| Blob-URL стикера отзывается между resolve и commit | URL удерживается до следующего resolve того же стикера |

Ещё четыре опровергнуты лишь потому, что их уже починили раньше в той же сессии,
и проверяющие читали исправленный код: проверка Origin от CSWSH, ключ хранилища,
переживающий выход, бан/удаление создателя админом и `env_file` у coturn.
