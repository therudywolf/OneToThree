## Detail

### 1. Storage quota is computed from a client-declared fileSize while the presigned PUT enforces no Content-Length

- **Severity** critical · **Status** UNVERIFIED (0 verifiers) · **Area** Security
- **Location** `server/src/routes/storage.ts:228`
- **Also reported as** `presigned-put-size-unbound-quota-bypass`

**How it fails**

A user who registered 30 seconds ago creates a chat, then POSTs /api/storage/upload-url with {fileName:"a.png", fileType:"image/png", chatId, fileSize: 1}. fileSize=1 clears both categoryLimitBytes and the getUserQuotaBytes/getUserUsageBytes check, and the returned presigned URL signs only Bucket/Key/ContentType — content-length is explicitly unsignable — so the client PUTs a 5 GiB body to MinIO and it is accepted. The attachments row records sizeBytes=1. Repeat 10x/minute (the route's own rate limit): ~50 GiB/min of real disk against 10 bytes of accounted usage. getCurrentUsageBytes() never crosses MEDIA_QUOTA_HIGH_WATERMARK, so maybeTriggerEviction never evicts, and getUserUsageBytes never returns USER_QUOTA_EXCEEDED. Grep confirms no HeadObject reconciler exists anywhere in server/src (the only HeadObjectCommand is the avatar commit at users.ts:368), so sizeBytes is never corrected. Result: the media volume fills and the service dies.

**Suggested fix**

Either (a) sign the upload size — pass ContentLength on the PutObjectCommand and drop 'content-length' from unsignableHeaders (proxies do not rewrite Content-Length on a body they pass through), or (b) require a POST /storage/upload-complete that does a HeadObject on the key, writes the TRUE ContentLength into attachments.sizeBytes, and deletes the object plus the row if it exceeds the declared size or the user's remaining quota. Until one of those exists, treat an un-HEADed attachment as size=categoryLimit for quota purposes rather than as the declared value.

### 2. POST /auth/verify resets the shared lockout counter before the 2FA gate, making the per-account TOTP lockout inert (previous #40 fix incomplete)

- **Severity** high · **Status** CONFIRMED (2 verifiers) · **Area** Backend
- **Location** `server/src/routes/auth.ts:487`

**How it fails**

Attacker has the victim's ECDSA private key (stolen/exfiltrated vault keyring) but not the TOTP secret — exactly the threat model the previous round's per-account TOTP lockout (#40) was added for. Loop: (1) POST /auth/challenge + POST /auth/verify with a valid signature -> auth.ts:487 runs `resetLockout(username)`, deleting `auth:fail:<username>`, and returns a fresh 300s `2fa_pending` token; (2) POST /auth/login/2fa four times with guessed 6-digit codes -> 4 `recordAuthFailure` increments, counter now 4 of 5, never locked; (3) repeat. The failure counter is reset to 0 on every iteration, so `checkLockout` at auth.ts:304 never fires no matter how many codes are tried. The only remaining bound is the per-IP rate limit (5 /verify per 15 min, 5 /login/2fa per hour), which is precisely what #40 said was insufficient because it is defeated by spreading across IPs. Net effect: the per-account TOTP lockout added in the previous round provides zero protection against the attacker it was written for.

**Suggested fix**

Do not clear the login-failure counter until the login is actually complete. Move `resetLockout(username)` out of the pre-2FA block: in the `existing?.isTotpEnabled` branch return the pending token WITHOUT resetting, and call `resetLockout(row.username)` only in /auth/login/2fa after `verifyTotp` + `consumeTotpCode` both succeed (mirroring /recovery/complete, which correctly resets only at auth.ts:654 after the step-up passes). Better still, keep TOTP failures in a separate `totp:<username>` namespace so a valid signature can never zero them.

### 3. PATCH /api/users/me lets a bare stolen session replace the account/device ECDH public key with no vault-unlock proof, redirecting peers' fan-out encryption to the attacker

- **Severity** high · **Status** CONFIRMED (2 verifiers) · **Area** Backend
- **Location** `server/src/routes/users.ts:516`

**How it fails**

Attacker steals only the session credential (fm_session cookie, or the `Authorization: Bearer` token native clients carry per session-cookie.ts:36-39) and never learns the vault password, so the vault keyring stays locked and no signature can be produced. Attacker generates their own P-256 ECDH keypair and sends `PATCH /api/users/me {"ecdh_public_key_jwk": "<attacker pub>"}`. ### 14. Sector-key wrap authenticates no metadata (no AAD), so an old wrapped key can be replayed as the current epoch

- **Severity** high · **Status** PLAUSIBLE (2 verifiers) · **Area** Encryption
- **Location** `client/src/lib/chat-logic.ts:72`

**How it fails**

Member M legitimately received wrap W3 = {kind:'CREATOR_AUTH_WRAP', v:2, epoch:3, ciphertext, iv, creatorEcdhPublicKeyJwk: <real owner>} carrying key K3. Member D is then kicked (epoch 4) and the owner rotates to K7@7. The server (or anyone with DB write access) re-writes M's row with the byte-identical ciphertext/iv of W3 but with the JSON field epoch changed to 7. Nothing detects this: readStoredSectorKeyEpoch reads the plaintext field (chat-logic.ts:211-223), the D2 check only compares creatorEcdhPublicKeyJwk (still the genuine owner), and AES-GCM authenticates only the 32 key bytes. M's buildSectorFrame adopts K3 as its CURRENT key and encryptOutboundText seals every new message with K3 — which departed member D still holds, so D reads all of M's post-departure traffic. Self-healing is also suppressed: the owner's reconcile compares only epochs (stored 7 < myEpoch 7 is false), so M is never re-keyed. The same primitive lets the server freeze the owner's own epoch label so shouldRotateGroupKey never fires after a departure.

**Suggested fix**

Bind the metadata to the ciphertext: pass the canonical header ({kind, v, chatId, targetUserId, epoch, creatorEcdhPublicKeyJwk}) as AES-GCM additionalData in sealBytes/unsealBytes, and have the unwrap side recompute the AAD from the values it independently expects (chat id from the URL, its own user id, the epoch it is claiming). A relabelled or cross-chat/cross-member replayed blob then fails authentication instead of being adopted.

**Counter-argument from verification**

> The mechanism the finding names (relabelling `epoch` in the plaintext JSON) grants the attacker no capability he does not already have, and the proposed AAD fix would not prevent the claimed harm.
> 
> 1. Who can do it. `server/src/routes/chats.ts:1450-1453` makes the wrapped-key PUT owner-only, so the only actor able to rewrite member M's row is the server/DB itself. That is in-scope per the D2 comment, so I did not refute on actor.
> 
> 2. The relabel is superfluous. `chat-crypto.ts:130-167` (`buildSectorFrame`) is the only consumer of a non-owner's stored key. It unwraps `me.encrypted_group_key` and returns it as `groupKey` unconditionally; `readStoredSectorKeyEpoch` at line 152 is used ONLY to index the local ring (`addRingEntry` / skip `entry.epoch >= currentEpoch`). Nothing on the member side ever compares its stored epoch against `chat.key_epoch` — that comparison exists only in owner paths (`group-key-rotation.ts:86-87`, `use-group-key-distribution.ts:56-61,134-153,265-269`). So a malicious server achieves the exact claimed outcome — M adopts K3, encrypts new traffic under it, departed D reads it — simply by NOT applying the owner's epoch-7 PUT to M's row and continuing to serve the genuine, untouched, self-consistent W3 blob. No byte is altered, no epoch is relabelled, and AES-GCM AAD over the header would authenticate perfectly.
> 
> 3. The proposed fix is circular for the epoch dimension. The reporter says the unwrap side should recompute AAD from "the epoch it is claiming." A member has no independent source for that epoch: `chats.key_epoch` is returned by the same server (`chats.ts` GET /chats/:id, consumed as `detail.chat.key_epoch`). Binding epoch into AAD only forces the server to also report a matching `key_epoch`, which it controls. Likewise the "freeze the owner's own epoch label so shouldRotateGroupKey never fires" claim is not a new primitive — the server can simply never bump `chats.key_epoch`, and `shouldRotateGroupKey` (group-key-rotation.ts:87) never fires.
> 
> Conclusion: against a malicious server, post-departure forward secrecy in this design is not enforceable client-side at all, and the AAD change does not move that needle. The reported failure sequence is therefore not a defect the fix addresses.
> 
> Residual (much narrower) truth: the wrap is not bound to chatId/targetUserId either, so a malicious server could copy owner O's blob for member M from chat X into M's row in chat Y, making M seal chat-Y traffic under K_X — readable by an X-member colluding with the server who is not in Y. That IS a genuine capability increase AAD would close, but it needs server compromise plus user collusion and is not the scenario reported. Rating it 'low' on that residual basis.

### 55. Encrypted call relay frames use a permanent static key with no AAD, sequence number or call binding — frames replay across calls and across the 1:1/group transports

- **Severity** medium · **Status** CONFIRMED (1 verifier) · **Area** Encryption
- **Location** `client/src/hooks/use-webrtc.ts:793`

**How it fails**

The relay key is K = HKDF(ECDH(IK_self, IK_peer), info='ForestMsg/call/1') — derived purely from the two long-lived identity keys, so it is byte-identical for every call between the same pair, forever, and identical for the 1:1 (`webrtc_signal` kind='relay_frame') and the group (`group_call:relay_frame`) transports. The frame carries only {ciphertext, iv, sampleRate}: no sequence number, no call/room id, no timestamp, no AAD. The server relays every frame and therefore holds a full recording of the ciphertexts. Concretely: the server captures Alice's frames from a 1:1 call on Monday, and during an unrelated group call on Friday re-injects them to Bob as `group_call:relay_frame` from Alice's user id. decryptBytes authenticates them (same K), pushFrame plays them, and Bob hears Alice saying words she never said in that call. The same primitive also allows reordering and dropping frames undetectably within a live call.

**Suggested fix**

Bind context into the AEAD: add an `additionalData` parameter to encryptBytes/decryptBytes and pass a canonical AAD of (transport tag | callId or roomId | senderUserId | monotonic frame counter). Reject frames whose counter is <= the highest already accepted for that peer+call. Better still, derive a per-call key by mixing a fresh per-call random salt (exchanged in the offer/answer, which is already integrity-protected by the signalling path) into the HKDF, so a captured call's frames are useless in any other call.

### 57. cacheSkipped creates a skipped-key bucket on every DH ratchet step and never removes empty ones, so state.skipped grows without bound and makes each skip O(buckets)

- **Severity** medium · **Status** CONFIRMED (1 verifier) · **Area** Encryption
- **Location** `client/src/lib/ratchet/double-ratchet.ts:263`

**How it fails**

Normal ping-pong: Bob receives a message carrying a new `dhPub`. `decryptRatchet` line 316 calls `cacheSkipped(state, state.dhRemote, prevN)` and line 321 calls `cacheSkipped(state, header.dhPub, counter)`. In the in-order case both loops execute zero iterations, but each has already inserted a bucket into `state.skipped`. So every DH ratchet step (i.e. roughly every reply in a two-way conversation) leaks up to two permanent `Map` entries which `serializeRatchet` (session-manager.ts:193-199) writes into the JSON that is stringified, AES-GCM encrypted and put into IndexedDB **on every single send and receive**. **Suggested fix**

### 108. Rate-limit allowList keys on request.ip, which is X-Forwarded-For-derived whenever TRUST_PROXY>0 — `X-Forwarded-For: 127.0.0.1` disables all rate limiting

- **Severity** low · **Status** PLAUSIBLE (2 verifiers) · **Area** Security
- **Location** `server/src/app.ts:299`

**How it fails**

Any deployment that reaches the API on a published port rather than exclusively through the appending reverse proxy — which the shipped `docker-compose.yml` does via `ports: "8080:8080"` — lets an attacker send `X-Forwarded-For: 127.0.0.1` on every request. proxy-addr with hop count 1 trusts the socket and returns the last XFF entry, so `request.ip` becomes `127.0.0.1`, `allowList` returns true, and *every* limiter is skipped: the global 100/min, the `/auth/challenge` 20/min, the `/auth/verify` 5-per-15-min scoped throttle (auth.ts:349), the `/devices/*` hourly caps, the admin 120/min. Unlimited auth attempts and unlimited request volume. The same header also poisons `recordLoginEvent`/audit rows, which log `request.ip`.

**Suggested fix**

Base the loopback escape hatch on the untrusted socket address, not on the proxy-derived one: `const raw = request.socket.remoteAddress?.trim(); return raw === '127.0.0.1' || raw === '::1' || raw === '::ffff:127.0.0.1'`. Additionally remove `ports: - "8080:8080"` from docker-compose.yml (use `expose: - '8080'` as docker-compose.prod.yml:167 already does), or bind it to `127.0.0.1:8080:8080`.

**Counter-argument from verification**

> Read server/src/app.ts:148-301, Caddyfile, docker-compose.yml, docker-compose.prod.yml, deploy.sh, and the memory prod-deploy notes.
> 
> What the reporter got right mechanically: `allowList` at app.ts:293-300 does key on `request.ip`, and with `trustProxy = 1` proxy-addr returns the LAST X-Forwarded-For entry when the socket peer is trusted (i=0 trusted, i=1 = last XFF entry returned). So a direct TCP connection carrying `X-Forwarded-For: 127.0.0.1` does yield `request.ip === '127.0.0.1'`.
> 
> What refutes the finding is the "direct TCP connection" premise:
> 
> 1. In the actual production topology the API is never reachable directly. Caddyfile:34-36 is `api.{$DOMAIN} { reverse_proxy api:8080 }`, and docker-compose.prod.yml:167 uses `expose: - '8080'` with no host publish. Caddy's reverse_proxy APPENDS the immediate peer address to X-Forwarded-For. So an attacker sending `X-Forwarded-For: 127.0.0.1` produces the upstream chain `127.0.0.1, <attackerIP>`; hop-count 1 skips the socket (Caddy) and returns index 1 — the LAST entry — which is the attacker's real IP, not `127.0.0.1`. The allowList returns false and every limiter applies. This is exactly what the hop-count logic at app.ts:148-169 was introduced to do, and the header comment at 150-157 states it verbatim; the reporter quoted the comment's premise but did not test through an appending proxy — their probe connected to Fastify directly, which is the one case the design already documents as out of scope (app.ts:288-289: "only safe when the API is not reachable from untrusted clients with spoofed X-Forwarded-For (edge proxy must strip/forbid client-supplied forwards)").
> 
> 2. The `ports: - "8080:8080"` cited from docker-compose.yml:104-106 is not a production artifact and is never merged with the prod file. docker-compose.yml:1-8 is a banner: "⚠️ LOCAL DEVELOPMENT ONLY — do NOT use this file in production… Deploy to prod with ./deploy.sh (docker-compose.prod.yml), never this file." deploy.sh:38 sets `COMPOSE_FILE="docker-compose.prod.yml"` and every invocation is `docker compose -f docker-compose.prod.yml` (single -f, no override merge, so the base file's `ports` list is never concatenated in). DEPLOY.md:181/186 and docs/guides/UPDATE.md:123 use the same single-file form. That same dev file also publishes Postgres with `forest/forest` and MinIO with `minio_secret_change_me` on the LAN — if you are running it on a hostile network, rate limiting is not the exposure that matters.
> 
> So the claimed failure ("every limiter is skipped on onetothree.ru, unlimited /auth/verify attempts") is not reachable in the shipped deployment. What remains is a real but narrow hardening gap: `docker-compose.yml:104-106` publishes 0.0.0.0:8080 while setting `NODE_ENV: production` (line 108) with no TRUST_PROXY, so trustProxy resolves to 1 (app.ts:168) on a dev box, and a LAN peer can spoof to 127.0.0.1 there. The proposed fix (key the escape hatch on `request.socket.remoteAddress`) is correct and cheap, and it would also stop the audit/login-event IP poisoning noted at login-event.ts:26 / devices.ts:248 for that same dev configuration.
> 
> Severity corrected high -> low: the bug only triggers on a configuration the repo explicitly forbids for production, and the production path is provably immune because Caddy appends.
