## Что закрыто в раунде 3

**Утечка конфиденциальности переписки**

- **Публикация ECDH-ключа теперь требует доказательства разблокировки хранилища**
  (`b4b0321`). `PATCH /users/me` принимал новый публичный ключ по одной лишь куке
  сессии — а это ключ, которым шифруют все пиры. Угнанная сессия молча
  перенаправляла входящие сообщения жертвы атакующему, без пароля хранилища.
  Теперь клиент подписывает одноразовый серверный nonce ECDSA-ключом из связки,
  который существует только после разблокировки. У `verifyVaultProof` появился
  `scope`, чтобы nonce, выданный для экрана восстановления, нельзя было потратить
  на подмену ключа.

- **X3DH-prekey'и снова случайные** (`df07ef9`). Они были HKDF от скаляра
  хранилища, то есть одноразовые ключи были детерминированной функцией
  долговременного секрета — утечка хранилища задним числом вскрывала X3DH-секрет
  каждой сессии. Теперь генерируются `crypto.getRandomValues`, приватные половины
  лежат в отдельном IndexedDB-хранилище, публикуются только публичные.
  Identity-ключ намеренно остался выводимым из хранилища: он и должен быть
  долговременным, его удостоверяет safety number.

**Потеря данных**

- **Кольцо эпох для медиа** (`d1bd36f`). У сообщений кольцо было с #32, у медиа —
  нет. Любая ротация ключа (то есть любое изменение состава группы) навсегда
  закрывала доступ ко всем ранее загруженным файлам. Кольцо теперь регистрируется
  при сборке крипто-контекста и используется как запасной путь расшифровки.

- **CAS по эпохе на сервере** (`b9ad287`). Две сессии владельца могли
  одновременно выпустить разные ключи под одним номером эпохи — группа
  раскалывалась на два ключа без возможности самолечения. Теперь инкремент эпохи
  условный (`WHERE key_epoch = ?`), проигравший получает 409 и прекращает
  ротацию, а не рассыпает второй ключ по составу.

**Укрепление**

- **v3-обёртка секторного ключа** (`d1bd36f`). AAD связывает `чат | эпоха |
  ключ создателя | участник`, и читатель собирает AAD из СВОЕГО контекста, а не
  из полезной нагрузки. Переставить эпоху, подсунуть блоб в другой чат или
  другому участнику больше нельзя — расшифровка падает. Ключи момента создания
  группы намеренно остаются v2: чата ещё не существует, привязывать не к чему.

- **Кадры relay-звонка** (`7d89b6c`). Ключ на пару собеседников был статическим
  навсегда, кадры шли без AAD и без счётчика. Теперь: nonce на звонок в
  `relay_offer`/`relay_answer` подмешивается в HKDF info (свой ключ на каждый
  звонок), AAD связывает направление и позицию, счётчик строго возрастает.

- **LiveKit :7880 закрыт** (`6e4c082`). Конфиг утверждал, что порт закрыт
  файрволом — **проба из интернета отвечала 200**. Плейнтекстовый HTTP/WS с
  room-JWT и Twirp-поверхностью в обход Caddy/Anubis/CrowdSec. Привязка к
  loopback положила бы звонки (Caddy — отдельный контейнер, ходит через шлюз
  docker-моста), поэтому entrypoint определяет шлюз в рантайме и биндится к
  нему. Проверено на живом деплое: публичный порт недоступен, через Caddy 200,
  медиапорт 7881 открыт.

- **Индекс `messages.media_path`** и **вызовы `clearBackupPending()`**
  (`6e4c082`) — три горячих запроса перестали сканировать таблицу; баннер
  «нет способа вернуться в аккаунт» теперь гаснет при сохранении файла ключа или
  записи фразы восстановления.

## Что сломано намеренно

Переход на v3 несовместим со старыми данными:

- групповые ключи в обёртке v2 при первой же ротации заменяются на v3;
- ранее опубликованные prekey'и невалидны — сессии переустанавливаются;
- клиенты без обновления перестают работать до перезагрузки.

На 5 тестовых аккаунтах это никого не задело.

## Что нашёл живой прогон, а модульные тесты — нет

Ревью и модульные тесты закрыли 118 находок и не увидели ни одной из пяти
ниже. Первые четыре нашёл `scripts/e2e-live/run.mjs` — два браузера против
развёрнутого прода; пятую — разбор того, почему одна из веток звонков вообще
никогда не выполнялась. Это и есть довод в пользу того, чтобы такой прогон был.

| Находка | Почему модульный тест не мог её увидеть |
|---------|-----------------------------------------|
| Гонка за одноразовым nonce: `crypto-login` и `activateVaultSession` публикуют ECDH-ключ одновременно, оба получают 403, ключ не публикуется вовсе (`531350d`) | Это гонка между двумя вызывающими сторонами в одной вкладке; оба набора тестов были зелёными |
| Лимит 30/мин на IP у publish-challenge ломал вход за общим NAT (`ea391a4`) | Лимит срабатывает только за настоящим периметром |
| `secrets/*` с правами 0600 от uid 1000 нечитаемы для api под uid 1001 → `livekit_enabled:false`, групповые звонки молча уходили в mesh (`7b97b7d`) | Права на файлы существуют только на хосте; `readSecret()` глотал EACCES |
| В режиме LiveKit клиент не слал `group_call:join` по WS → о звонке не узнавал никто, кроме звонящего (`7b97b7d`) | Ветка LiveKit была недостижима на проде, пока ключи не читались |
| Групповой аудио-relay шифровал кадры без AAD, без счётчика и одним статичным парным ключом на все комнаты (`88c8f08`) | Фикс #5 был применён к 1:1-relay; вторая реализация того же примитива осталась без него, и ни одно из 118 ревью-замечаний её не выделило |

Живьём подтверждены: создание группы с клиентским sector-ключом и немедленной
ротацией на v3, расшифровка в обе стороны, вложение после ротации ключа
(кольцо эпох), групповой звонок через SFU с проверкой сокета к LiveKit, звонок
1:1, привязка устройства и восстановление по фразе.

Отдельно закрыт **WebSocket-relay** — запасной транспорт для развёртываний без
SFU и TURN, который на этом проде не выполняется никогда (coturn и LiveKit
подняты), и потому не имел живого покрытия вообще. Сценарий `relay` подменяет в
браузере два ответа, которыми эта ветка и определяется (`/call/config` в режиме
origin_safe и падающий `/ice-servers`), — дальше всё настоящее: кадры
пересылает реальный сервер, шифрует реальная крипта.

Групповая половина — именно доказательство, а не дымовой тест: удалённый поток
возникает только после того, как кадр **откроется**, поэтому счётчик участников
2 означает, что AAD и порядковый номер прошли туда-обратно между двумя
браузерами. Результат: обе стороны видят по 2, по 20 кадров в каждую сторону,
ни одного обращения к SFU; в 1:1 — по 85 кадров в каждую сторону.

Попутно выяснено, что условие `!hasRelay && !p2pAllowed` недостижимо ни при
одном успешном ответе `/ice-servers`: маршрут отдаёт 503 всегда, когда TURN не
разрешается, поэтому единственный вход в relay — сбой самого запроса. Это и
задумано, но три тернарных выражения в обработчике имеют мёртвые ветки.

## Аудит: 21 → 1 (заменён next-pwa)

Владелец решил всё-таки чинить. Сработал единственный оставшийся путь —
**переход с `next-pwa` на `@serwist/next`** (`1b82315`). Осталось одно
предупреждение: `brace-expansion`, достижимый через плагины `eslint-config-next`;
его снял бы eslint 10, но тот ломает `npm ci` (см. `2ccecee`).

Serwist компилирует исходник worker'а, а не генерирует его из конфига, поэтому
правила переехали в `client/src/app/sw.ts`. Путь вывода намеренно не изменился
(`public/sw.js`): его регистрирует `push-subscription.ts`, и у уже установленных
PWA эта регистрация есть.

Матчеры вынесены в `lib/sw-cache-rules.ts` и **впервые покрыты тестами** (9).
Это важно ровно для одного из них: Cache Storage адресуется по URL и общий для
всех аккаунтов браузера, и слишком широкое правило однажды отдавало пользователю
B список устройств пользователя A — имена, id, последний вход — на все 5 минут
TTL после смены аккаунта. Тесты фиксируют узкую версию, включая хвост
`(\/|\?|$)`, который держит персональный `/api/gif-favorites` снаружи, впуская
общий прокси `/api/gif`.

Заодно убран молчаливый `try/catch` вокруг плагина: он проглотил бы отсутствие
next-pwa и собрал бы сборку вообще без service worker — push и офлайн просто
исчезли бы, без единой строчки в логе.

Ниже — что было проверено до этого и почему остальные пути не сработали.

## Почему остальные подходы не сработали

Все они сводятся к одному устаревшему `brace-expansion`, до которого доходят
через `minimatch` → `glob`. Проверено экспериментально, чтобы это не пришлось
выяснять заново:

| Попытка | Результат |
|---------|-----------|
| Обновить `brace-expansion` в линиях 1.x / 2.x | Бэкпорта нет: диапазон уязвимости `<=5.0.7` покрывает их целиком |
| `overrides` на `brace-expansion: ^5.0.8` для всего дерева | Закрывает все 23 и **ломает сборку**: 5.x сменил форму экспорта, `minimatch@3` внутри плагинов eslint падает с `expand is not a function` |
| eslint 9 → 10 (переходит на `minimatch@10`) | Проходит линт, типы и 617 тестов — и **ломает образ**: `npm ci` строже, чем `npm install`, eslint 9 остаётся через peer у typescript-eslint, и два мажора дерутся за поднятый `@eslint/js` |
| `overrides` на `workbox-build` / `workbox-webpack-plugin` → `^7.4.1` | npm не применяет через мажорную границу (`^6.5.4` → `^7.4.1`) и оставляет 15 записей `invalid` — даже после полной пересборки lockfile. Запись `invalid` в дереве это тоже сломанный `npm ci` |
| `@ducanh2912/next-pwa@10.2.9` (поддерживаемый форк next-pwa) | Тянет `workbox-build@7.1.1` с **той же** цепочкой (`glob@^7`, `@surma/rollup-plugin-off-main-thread`). Не помогает |
| `@serwist/next` (`glob@13` — чисто) | **Это и сработало** — см. раздел выше. Оценка «останется ~10 от плагинов eslint-config-next» оказалась пессимистичной: осталось 1 |

Что **было** сделано и работает: `vitest` 4 (у `@vitest/coverage-v8@4` больше нет
`test-exclude`, а с ним `glob` и `minimatch`) и `@testing-library/jest-dom` 7.
Плюс пять правок кода, которые нашли новые правила eslint 10 прежде, чем его
пришлось откатить, — все настоящие и валидные под девяткой.

## Опровергнуто при ревью раунда 2

Сообщено, но не подтвердилось при разборе кода. Записано, чтобы не поднимать
заново.

| Находка | Почему отклонено |
|---------|------------------|
| Записи кольца разворачиваются без привязки к владельцу | Запись попадает в кольцо только после проверки привязки; `buildSectorFrame` — единственный писатель |
| `recordFailure` через EVAL против `checkLockout` через GET/TTL | Оба пути деградируют одинаково; скриптинг на развёрнутом Redis доступен |
| `skipOnError` у Redis-лимитера открывает проход | Лимитер падает обратно на in-memory store, а не пропускает проверку |
| Удаление личного чата навсегда вешает вложения на квоту | Строки квоты уходят вместе с чатом |
| Blob-URL стикера отзывается между resolve и commit | URL удерживается до следующего resolve того же стикера |

Ещё четыре опровергнуты лишь потому, что их уже починили раньше в той же сессии,
и проверяющие читали исправленный код: проверка Origin от CSWSH, ключ хранилища,
переживающий выход, бан/удаление создателя админом и `env_file` у coturn.
