# How to read this file

For each finding:
- **Severity** — P0 (data loss / login broken / sec breach), P1 (degraded core feature), P2 (UX/code-debt), P3 (nice-to-have).
- **Locator** — `path:line` or pattern. Always file-anchored so a future agent can `Read` it directly.
- **Evidence** — what I actually saw, not paraphrase.
- **Fix sketch** — minimal, opinionated, no prose.

Rules of engagement before acting on any item:
1. Re-`Read` the locator. Refactors may have moved code since this audit.
2. If a P0 has tests, run them first to capture the regression — then fix — then re-run.
3. Don't silently bundle unrelated cleanup into the same commit.

# 1 · P0 — break or risk break

## P0-1 · Half the client `fetch` sites bypass the no-store fix

- **Locator:** `client/src/lib/{chat-crypto,chat-message-transport,fanout-crypto,outbox,push-subscription,client-wipe,avatar-cache}.ts`, `client/src/lib/ice-servers.ts:146`.
- **Evidence:** `grep " await fetch(" client/src/lib` returns 11 raw `fetch()` call sites that go straight to the network with default `cache:` (= `default`). They bypass `fetchWithTimeout` (`client/src/lib/api/fetch.ts`) — which now defaults to `cache: 'no-store'`. Among them: `messages/send` (twice), fan-out device-key fetch, outbox replay, push subscription. So the SW + browser HTTP cache can still serve stale responses for everything except `auth/*` (which is also covered by server-side `Cache-Control` we just shipped).
- **Why P0:** the same class of bug that froze login can re-emerge for *device-key fetch* (causes silent decrypt failures: stale `/users/:id/devices` returns the prior list of ECDH keys → fan-out sends to dead devices → recipient sees nothing).
- **Fix sketch:** route every `lib/**` `fetch()` through `fetchWithTimeout`. One commit, no behaviour change, ~30 LOC delta.
- **Test:** add a vitest that mocks `globalThis.fetch` and asserts every helper passes `cache: 'no-store'` (or omits `cache` so the wrapper applies the default).

## P0-2 · Migration journal is out of order

- **Locator:** `server/drizzle/meta/_journal.json` entries 33–43, plus duplicate filenames `0035_messages_pinned_and_muted.sql` and `0035_same_molly_hayes.sql`, missing `0041_*.sql`.
- **Evidence:** journal sequence reads `…0034 → 0035_pinned → 0035_molly → 0037 → 0038 → 0039 → 0033_discussion_link → 0036_shares → 0040 → 0042 → 0043` (idx 39 is `0033_chats_discussion_link`). On a fresh DB Drizzle replays in journal order — works today by coincidence (no FK dependencies broken in this ordering) but any future migration that touches the same table as `0033` cannot rely on the file-number ordering.
- **Why P0:** silent prod risk on next add. We already tripped on the `0035_same_molly_hayes` duplicate (handoff 2026-04-22d). One more drift and CI green will not match prod.
- **Fix sketch:**
  1. Rename `0035_same_molly_hayes.sql` → `0041_same_molly_hayes.sql` (same DDL); update journal `tag` and bump `idx` accordingly. Verify journal-order = filename-order.
  2. Add a CI check `scripts/check-drizzle-journal.js` that asserts `entries[i].idx === i` and `entries[i].tag` sorts ASCII-ascending.
  3. Test: `npm run db:push:docker` against a clean DB.
- **Caveat:** never rewrite the journal on a DB that has already applied the entries in production. Verify `__drizzle_migrations` content first; if prod has applied with the current order, only renaming the file in-repo is safe (Drizzle keys by `tag`).

## P0-3 · Server reads `request.body` without size cap on large endpoints

- **Locator:** `server/src/routes/messages.ts`, `server/src/routes/users.ts` (PATCH `/me`), `server/src/routes/keys.ts` (one-time prekey upload).
- **Evidence:** `app.register(rateLimit, …)` exists globally in `server/src/app.ts:177`, but I see no `bodyLimit` on `Fastify({ … })`. Default is 1 MiB but vault blob, prekey batch, fan-out `ciphertexts[]` for groups can grow. A single oversized POST returns a 413 — fine. **But** there is no per-route `bodyLimit` for `messages/send` carrying a base64 PUBLIC payload (CLAUDE.md notes PUBLIC chats ship plaintext base64). A 1 MiB cap × N concurrent uploaders is enough to choke the event loop.
- **Why P0:** trivially exploitable by an authenticated user; no abuse mitigations beyond rate limit.
- **Fix sketch:** set explicit `bodyLimit` per route: 64 KiB for `messages/send`, 256 KiB for vault, 32 KiB for prekey upload (already enforced by zod max but Fastify rejects earlier).

## P0-4 · `fanout-crypto` `Promise.allSettled` still drops failed slots silently

- **Locator:** `client/src/lib/fanout-crypto.ts` (search `allSettled`).
- **Evidence:** still flagged in `docs/audits/AUDIT.md` as C4 (2026-04-22). No commit since touches that file. Re-confirmed in repo today.
- **Why P0:** if encryption fails for one of the recipient devices, that device gets no slot, recipient sees nothing, sender sees no error.
- **Fix sketch:** return `{ slots, failedDeviceIds }` from `buildFanoutSlots`; `useSendMessage` shows a toast `"Sent to N of M devices"`; outbox queues a retry for failed device IDs only.

# 2 · P1 — degraded behaviour

## P1-1 · `chat-message-transport.ts` raw fetch + no `cache: 'no-store'` + no timeout

- **Locator:** `client/src/lib/chat-message-transport.ts:122,143`.
- **Evidence:** two raw `fetch(${API_URL}/messages/send …)` calls, no AbortController, no `cache:`. With the default 60-second browser network timeout, a flaky cell connection blocks the send-button forever (UI shows spinner indefinitely).
- **Fix sketch:** swap to `fetchWithTimeout` (already exists). Guard with try/catch + outbox enqueue on failure (outbox path already exists).

## P1-2 · `WS` reconnect adds a fresh `online` listener every cycle

- **Locator:** `client/src/lib/api/socket.ts` — search `addEventListener('online'`.
- **Evidence:** flagged as C3 in 2026-04-22 audit. Still present.
- **Why P1:** every reconnect leaks one listener → on long-lived sessions outbox flushes N times per single `online` event → message duplication risk (server dedupes by `client_message_id` so it's bounded, but wasted work + jank).
- **Fix sketch:** store the handler in a module-level `let`, check before `addEventListener`, remove in `disconnect()`.

## P1-3 · `lookupUsers` typing event refresh re-sets TTL with stale stored TTL

- **Locator:** `client/src/hooks/use-chat-realtime.ts:54-66` (after our recent 6000ms bump). The first `setTypingUser` happens immediately; the deferred `lookupUsers().then(...)` calls `setTypingUser` again with `6000`. If the lookup takes 5+ seconds, the indicator was about to expire — re-setting puts it back to 6 seconds *from now*, effectively pinning it for up to 11 seconds total per typing event.
- **Why P1:** indicator can flicker on/off for slow networks. Mitigation: only re-set if the *username* changed; otherwise leave the existing entry alone.
- **Fix sketch:**
  ```ts
  if (row.username !== known) setTypingUser(activeChatId, msg.user_id, row.username, 6000)
  ```

## P1-4 · `chat-terminal.tsx` `useLayoutEffect` cleanup doesn't reset `data-stabilizing` on unmount

- **Locator:** `client/src/components/chat/chat-terminal.tsx` `useLayoutEffect` around line 466.
- **Evidence:** the safety timeout we just added clears within 280 ms, but if the component unmounts mid-rAF we leak the attribute on the next mount of a sibling chat panel (rare — only impacts MD3 modal flows).
- **Fix sketch:** in cleanup, also reset `data-stabilizing="false"`.

## P1-5 · `next-pwa` is unmaintained on Next 16

- **Locator:** `client/next.config.js:88-136`.
- **Evidence:** `next-pwa@5.x` last release 2023; Next 16 ships App Router with edge changes; `cacheStartUrl: false` is honoured but other knobs (`buildExcludes`, `dynamicStartUrlRedirect`) silently no-op. Bug surface for cache invalidation.
- **Fix sketch:** plan migration to `@serwist/next` (active fork). Schedule for the next dependency sweep — not urgent until next-pwa actually breaks a build.

## P1-6 · `manifest.ts` icon set has no `96/144/256` PNG and one icon does double duty

- **Locator:** `client/src/app/manifest.ts:65-90`.
- **Evidence:** only 192/512. Android 13+ launchers honour 96/144 for shortcuts; absence makes the app icon look low-res in the launcher carousel. Same `192.png` is reused for `any` + `maskable` purposes; maskable should have its own asset with safe area baked in.
- **Fix sketch:** generate `icon-96.png`, `icon-144.png`, `icon-256.png` from the existing logo; carve a separate `icon-maskable-192.png` / `512.png` with 80% safe area; update manifest.

## P1-7 · GIF picker shows no actionable state when `TENOR_API_KEY` is unset

- **Locator:** `client/src/components/chat/composer-picker-panel.tsx:639-642`.
- **Evidence:** falls through to `composer.gifPopular` ("Popular GIFs") even when the server returns `[]` because the env is missing. Operator never knows to set the key.
- **Fix sketch:** server returns `{ items: [], reason: 'PROVIDER_NOT_CONFIGURED' }`; client shows admin-visible "GIF provider is not configured. Set `TENOR_API_KEY` or `GIPHY_API_KEY`." for users with `role: 'admin'`, generic empty state for others.

## P1-8 · Sticker grant-chat is fire-and-forget with no retry / no UX feedback

- **Locator:** `client/src/lib/api/stickers.ts:368-385` (`grantStickerPackToChat`).
- **Evidence:** wraps in `try{}catch{}` with comment "non-fatal". If the call drops on transient network the recipient sees the broken-asset CTA instead of the sticker. They CAN clone, but the seamless path is gone.
- **Fix sketch:** queue grant in `outbox` with `retry: 3`; on each successful grant, optionally fire a WS `sticker_pack_granted` event so recipient's `sticker-bubble` can `loadStickerDisplayUrl` retry.

## P1-9 · `start-url` cache disabled — cold start may re-fetch root every session

- **Locator:** `client/next.config.js` `cacheStartUrl: false`.
- **Evidence:** intentional fix from `988dcf2`, but PWA "open from home screen offline" now shows the offline page (`client/public/offline.html`) instead of last cached shell.
- **Why P1:** trade-off — accepting because the alternative was the login-pin bug.
- **Fix sketch:** custom registerRoute for `'/'` that does `NetworkOnly` for HTML responses but allows the precached `_next/static/chunks/app/page-*.js` to hydrate from cache. Defer until PWA-offline UX becomes a complaint.

## P2-2 · 5 routes have no per-route rate limit

- **Locator:** `server/src/routes/{call,chats,gif-favorites,vault,webrtc}.ts`.
- **Evidence:** `grep -L 'rateLimit' server/src/routes/*.ts` (excl. tests).
- **Why:** global rate limit (100/min) covers basic abuse, but `chats.ts` has `POST /chats/:chatId/invite` and `POST /chats/:chatId/leave` — both should have tighter caps to limit churn-spam in invite slugs.
- **Fix sketch:** add `config: { rateLimit: { max: N, timeWindow: '…' } }` per sensitive endpoint. Suggested values: invite create 10/min, leave 20/min, vault sync 60/min.

## P2-3 · `as any` casts in `webauthn-vault.ts` (7 sites)

- **Locator:** `client/src/lib/webauthn-vault.ts` lines 25, 121, 136, 141, 183, 188.
- **Evidence:** WebAuthn `largeBlob` extension typings are missing from lib.dom. The casts are isolated. Acceptable today but worth a `types/webauthn-largeblob.d.ts` shim.

## P2-4 · `console.debug` calls in production code

- **Locator:** `client/src/hooks/use-media-recorder.ts:98`, `client/src/hooks/use-pwa-install.ts:63`, `client/src/lib/api/avatar.ts:24,51`.
- **Evidence:** `next.config.js` strips `console` in production except `error|warn`. So these are stripped — but they leak into dev DX (noise) and are not gated by `if (process.env.NODE_ENV !== 'production')`.
- **Fix sketch:** wrap each call in a `__DEV__` check or move to `app.log`-style util.

## P2-5 · `silence-console.tsx` overrides `console.log`/`debug` globally on mount

- **Locator:** `client/src/components/silence-console.tsx`.
- **Evidence:** `console.log = noop; console.debug = noop`. Useful for prod but kills the new boot diagnostic from `auth-provider.tsx` (we used `console.info` — survives — but next person who switches to `.log` will silently lose telemetry).
- **Fix sketch:** comment in `silence-console.tsx` calling out which methods stay live; consider gating on `?debug=1` query param.

## P2-6 · `chatTypeEnum` includes `'channel'` but the channel UI is partial

- **Locator:** `server/src/db/schema.ts:17-22`, comment in `CLAUDE.md` "channel backend+schema shipped; full UI flow still partial".

## P2-7 · No `bodyLimit` on Fastify root + no per-route `attachValidation`

# 5 · Cross-cutting observations

## Auth/session flow

The login path (`POST /auth/challenge` → ECDSA-sign nonce → `POST /auth/verify` → `GET /auth/me`) is now hardened end-to-end:
- Server stamps `Cache-Control: no-store` on every `auth/*` response (`server/src/routes/auth.ts` `onSend` hook).
- Cookie is `SameSite=None; Secure` whenever HTTPS (`server/src/lib/session-cookie.ts:63-72`).
- Client `fetchMe` no longer hits SW or HTTP cache (`client/src/lib/api/fetch.ts`).
- `/reset-pwa` rescues users stuck on a stale Service Worker.

Outstanding gap: **P0-1**. Many lib modules still use raw `fetch()`. Until those are migrated, an analogous bug to the login-cache could appear in a different code path (most likely device-key fetch → silent decrypt fail).

## Crypto correctness

The 2026-04-22 audit's C5 (vault AAD downgrade) is **still open**. Re-confirmed: `client/src/lib/vault.ts` `wrapPrivateJwkWithPin` does not pass `additionalData` to `crypto.subtle.encrypt`. Promote to P0 in next pass.

The Double Ratchet bootstrap (`client/src/lib/ratchet/dr-bootstrap.ts`) is gated by `NEXT_PUBLIC_DR_ENABLED`. Tests exist for `kdf` and `safety-number` but not for the bootstrap orchestration itself. Adding an e2e under `client/tests/e2e/` for "DR off → DR on toggle" would catch regressions in the off-by-default state.

## Observability

Server boots with structured Pino, request IDs are stamped via `onRequest` hook (`server/src/app.ts:240-242`). Client has no error reporter wired (no Sentry, no posthog). The `[p13:boot]` console.info we just added is dev-only. **Recommend** a minimal `report.ts` that POSTs unhandled rejections to a `/api/_telemetry` server route for prod debugging — gated by user opt-in to keep zero-trust posture.

## PWA posture

Service Worker assumptions:
- `skipWaiting: true` + `clientsClaim()` — new SW takes over on next nav.
- Precache currently 200+ entries (every chunk). Bandwidth-heavy install.
- No background sync registered for outbox replay; relies on `online` event listener (see P1-2).

Web App Manifest:
- `display_override: ['window-controls-overlay', 'standalone', 'browser']` — desktop PWA gets WCO. Make sure the title-bar drag region is set in CSS (`-webkit-app-region: drag`); not seen in current `globals.css`.
- `launch_handler.client_mode: ['navigate-existing', 'auto']` — good; prevents new windows on URL launches.
