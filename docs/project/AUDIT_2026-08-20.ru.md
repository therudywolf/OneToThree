## 1. Коммиты и сборки

53 коммита с 13 августа — в основном точечные исправления по итогам живых
прогонов (гости, звонки, Android, Lite, десктоп). Формулировки заголовков
описывают дефект, а не «фиксы», история читается — это редкость и её стоит
сохранить.

**Найдено и починено:**

- **`npm run test:all` не мог пройти на Windows.** `scripts/lib/env-value.test.mjs`
  спавнил `bash` с PATH, а на Windows это `C:\Windows\System32\bash.exe` —
  WSL-релей, который без установленного дистрибутива отвечает
  `execvpe(/bin/bash) failed` и ненулевым кодом. Десять тестов падали **не по
  сути**, а из-за интерпретатора. Соседний `build-stamp.test.mjs` умел это
  пережить (свой `hasBash`-гард), но ценой того, что все его 28 тестов на
  Windows молча **пропускались**.
  → `scripts/lib/test-bash.mjs`: общий резолвер (сначала `TEST_BASH`, потом Git
  Bash по стандартным путям, потом PATH; проба `echo ok` отсеивает релей),
  `hasBash` для честного skip. Оба файла переведены на него. Итог: 19 ✅/10 ❌ →
  **47 ✅**, и 28 тестов деплой-скрипта впервые реально исполняются на этой
  машине. **СДЕЛАНО**
- **`tauri-build.yml` остался на Node 20**, когда `0ccde3e` поднял остальные
  джобы до 22; в `release.yml` два шага после того же коммита сохранили подпись
  «Set up Node 20» при `node-version: 22`. Первое — расхождение мажора между
  десктопным бандлом и всем остальным, второе — ложный след в логах.
  **СДЕЛАНО**
- **`scripts/` не линтовался вообще**, и это не безобидный пробел: в
  `install.mjs` уехала ссылка на необъявленный `adminUsername`, из-за чего
  CLI-установщик падал с `ReferenceError` сразу ПОСЛЕ успешного
  `docker compose up` — стек поднят, оператор видит крэш, инструкция «как стать
  владельцем» не печатается, а сам ник в `.env.lite` из CLI не попадал никогда.
  `node --check` такое не видит (файл разбирается), `no-undef` находит за
  миллисекунды. → `scripts/eslint.config.mjs` + `npm run lint:scripts`
  (включён в `npm run lint`), покрывает `scripts/`, `client/scripts`,
  десктопные и мобильные скрипты; харнессам `e2e-live` выданы браузерные
  глобалы, потому что они шлют функции в страницу. **СДЕЛАНО**

**Про CI без иллюзий.** Все воркфлоу, кроме двух, стоят на `workflow_dispatch`
(биллинг Actions выключен решением владельца). Исключения: `release.yml` — по
пушу тега `v*`, и `claude.yml` — по `issue_comment`. То есть **тег включает
биллинг**. Реальный гейт качества сегодня — локальный прогон и живые харнессы;
`npm run test:all` в этой роли теперь работает на обеих платформах, что и было
основной целью правки выше.

## 2. Standalone-версия (Lite)

Проверено: `docker-compose.lite.yml`, `scripts/lite/*` (CLI + GUI-визард),
контрактный тест «установщик ↔ compose», `docs/guides/LITE.md`.

Состояние **хорошее**. Контрактный тест закрывает самый неприятный класс
ошибок — переменная, которую compose читает, а установщик не пишет (в контейнер
приезжает пустая строка: молча выключенная фича или пустой секрет), и наоборот.
Отдельными тестами закреплено, что ни один внутренний сервис не публикует порт
наружу и что MinIO по умолчанию слушает loopback.

**Найдено и починено:**

- **У Lite не было первого администратора.** Установщик заканчивал работу
  строкой «зайди в psql и выполни UPDATE». Половина установок так и оставалась
  без админки. → установщик (и CLI, и GUI) спрашивает ник, пишет
  `OT_ADMIN_USERNAME` → `ADMIN_BOOTSTRAP_USERNAME`, API повышает аккаунт на
  старте. Значение проходит через `assertSingleLine` — `.env.lite` построчный, и
  ник с переводом строки иначе дописал бы в него произвольные переменные (ровно
  ту дыру уже чинили для поля домена). **СДЕЛАНО** (см. §3)

- **У Lite не было бэкапа.** `scripts/backup*.sh` и `backup.ts` зовут
  `docker compose` без файла и env-файла, то есть резолвят `docker-compose.yml`
  и чужой проект; на Lite они либо падают на обязательной переменной пароля БД,
  либо тихо разговаривают с другим стеком. Плюс MinIO в Lite за профилем — при
  выключенном медиа контейнера нет вообще, а прод-скрипт считает это фатальной
  ошибкой. → `scripts/lite/backup.mjs` (`npm run lite:backup` / `lite:restore`):
  pg_dumpall + каталог MinIO, если он есть, + `.env.lite` — последнее намеренно,
  потому что дамп без JWT-секрета и ключа обёртки TOTP восстанавливается в базу,
  которую никто не может прочитать. Архив кладётся 0600, и инструмент прямо
  говорит, что он равносилен доступу к серверу. Восстановление требует
  `RESTORE_CONFIRM=YES`. **СДЕЛАНО**

**Остаётся (не делалось, осознанно):**

- Медиа-драйвер на локальной ФС без MinIO — в роадмапе; для «одной командой» это
  самый весомый оставшийся кусок (сейчас медиа = ещё один контейнер + вопрос про
  публичный URL объектного хранилища, на котором спотыкается больше всего людей).
- Встроенный LiveKit — там же в роадмапе; сейчас звонки в Lite без внешнего SFU
  идут по WebSocket-relay, и это честно описано.

## 3. Админка

### Почему «не работает»

Причина воспроизводится по документации, а не гадается.

`DEPLOY.md` и `DEPLOY.ru.md` в разделе «Создать первого администратора» велели
выполнить:

```sql
UPDATE users SET role='admin' WHERE username='…';
```

**Одного `role` мало.** В коде два разных уровня: `role='admin'` открывает
`/admin` и пускает в панель, а `user_group='creator'` — это то, что проверяет
каждое привилегированное действие (`server/src/routes/admin.ts`: выдача и снятие
админских прав → `CREATOR_ONLY`). Администратор, созданный по инструкции из
DEPLOY, получал панель, в которой половина кнопок отвечает `403` без единого
объяснения. `README.md` и `docs/guides/FIRST_START.md` при этом выставляли оба
поля — то есть четыре документа в одном репозитории учили двум разным вещам, и
ровно один из них ошибался в сторону поломки.

Вторая причина, системная: **первый администратор появлялся только через psql
внутри контейнера БД**. Никакого seed, никакой переменной, никакой команды. Для
self-hosted продукта это худший из возможных первых шагов.

### Что сделано

1. **Бутстрап первого админа.** `ADMIN_BOOTSTRAP_USERNAME=<ник>` в окружении API:
   на старте аккаунт повышается до `creator` (и `role='admin'`, синхронно — как
   это делают сами админ-роуты). Свойства выбраны так, чтобы переменную было
   безопасно забыть в `.env`:
   - **идемпотентно и самообезвреживается** — как только на сервере есть хоть
     один `creator`, переменная не делает ничего (нельзя вернуть права тому,
     кого сняли);
   - **никогда не создаёт аккаунт** — только повышает существующий, поэтому сама
     по себе никому ничего не даёт: ключи всё так же только у владельца аккаунта;
   - **громко в обе стороны** — нет такого ника, будет предупреждение с готовым
     рецептом, а не тишина;
   - **не фатально** — сбой БД на старте не мешает API подняться.
   Пишет строку в `admin_audit_log` с `admin_user_id = NULL` (действие инстанса,
   не человека). Покрыто `server/src/lib/admin-bootstrap.test.ts`. **СДЕЛАНО**
2. **Документация исправлена** — DEPLOY(.ru), README(.ru), FIRST_START(.ru),
   LITE.md: везде сначала переменная, а ручной SQL — со **обоими** полями и
   объяснением, почему одного `role` мало. **СДЕЛАНО**
3. **Панель сама объясняет проблему.** Если создателя на сервере нет, вкладка
   CONFIG пишет это прямым текстом и даёт оба рецепта — вместо загадочного 403.
   **СДЕЛАНО**

### Настройки инстанса — новое

Раньше **любая** настройка сервера жила только в `.env` и требовала перезапуска.
Появился слой рантайм-настроек: `instance_settings` (drizzle **0065**),
`server/src/lib/instance-settings.ts`, `GET/PATCH /api/admin/settings`,
`GET /api/admin/instance`, вкладка **CONFIG** в панели.

Контракт: **эффективное значение = переопределение в БД ?? env ?? встроенный
дефолт**. Строка в таблице появляется только если админ действительно менял
ручку, а «Сбросить» её удаляет — то есть панель это слой поверх `.env`, а не
замена ему (важно для тех, кто держит конфиг в git).

Что стало живым (читается **на каждый запрос**, без перезапуска):

| Ручка | env | Где применяется |
|---|---|---|
| `open_registration` | `FEATURE_OPEN_REGISTRATION` | ветка регистрации в `POST /auth/verify` |
| `guest_link_ttl_hours` | `GUEST_LINK_TTL_HOURS` | создание гостевой ссылки |
| `guest_meeting_seats` | `GUEST_MEETING_SEATS` | места на новой ссылке-встрече |
| `guest_chat_ttl_hours` | `GUEST_CHAT_TTL_HOURS` | жизнь гостя временного чата |
| `guest_max_links_per_user` | `GUEST_MAX_LINKS_PER_USER` | потолок живых ссылок |
| `guest_max_active` | `GUEST_MAX_ACTIVE` | потолок живых гостей |

Осознанные границы:

- **Флаги фич (`FEATURE_*`) остались только в окружении.** Они решают, будет ли
  группа роутов вообще зарегистрирована при старте (`app.ts`), поэтому
  переключатель «на лету» показывал бы «включено» на фиче, у которой все
  эндпоинты отвечают 404. В панели они видны, но только для чтения — это всё
  равно лучше, чем читать `.env` по SSH. Исключение — открытая регистрация: она
  никогда не была гейтом роута, это ветка внутри хендлера, поэтому её и можно
  переключать вживую.
- **Бюджеты рейт-лимитов не в списке.** Они потребляются один раз при
  регистрации лимитера; живое значение в панели врало бы о том, что реально
  применяется.
- **Запись — только `creator`.** Эти ручки решают, может ли посторонний завести
  аккаунт и сколько сервера способна съесть одна гостевая ссылка; обычный админ,
  который может тихо снова открыть регистрацию, — это путь эскалации, а не
  удобство. Каждое изменение пишется в аудит-лог вместе с запрошенным и
  фактическим (после зажатия в диапазон) значением.
- **Кэш на 5 секунд.** Прод крутит больше одного процесса, и чисто локальный
  кэш дал бы воркерам разное представление о конфигурации до самого рестарта.
  Локальная запись сбрасывает кэш немедленно, поэтому админ видит эффект
  сразу. При недоступной БД слой отдаёт env/дефолты, а не падает.

Заодно `/capabilities` начал отдавать `openRegistration`, а экран входа —
показывать закрытую регистрацию: вкладка «Создать аккаунт» гаснет, вместо формы
появляется объяснение. Раньше человек проходил весь обряд (ник, пароль
хранилища, подтверждение, согласие) и получал `REGISTRATION_DISABLED` в конце.
Фейл-open: пробник по умолчанию `true`, сбой сети не спрячет регистрацию на
сервере, который её разрешает.

**`GET /api/admin/instance`** отвечает на «что у меня вообще запущено»: версия и
коммит живой сборки, версия Node, аптайм, реально ли отвечают Postgres и Redis
(пинг ограничен 1.5 с — эту карточку открывают именно тогда, когда что-то
сломано, и вечное ожидание было бы худшим её поведением), настроен ли LiveKit,
сколько сейчас живых гостей и ссылок, сколько на сервере создателей.

Покрыто `server/src/routes/admin-settings.test.ts` (8 тестов): только создатель
пишет, `null` **очищает**, а не пишет дефолт, значение зажимается в диапазон,
переопределение реально доезжает до `/capabilities`, и закрытая регистрация
действительно не создаёт строку в `users`.

**Остаётся:** админка по-прежнему целиком русскоязычна и вне системы токенов
(13 из 15 нарушений линтера — её бейджи групп, и они законные: три роли
различаются только оттенком). Массовых действий над отчётами нет. Экспорт
аудит-лога в CSV есть только для login-events.

## 4. Временные звонки и чаты

Инвентаризация всех кнопок гостевого контура и добор недостающих.

**Что уже было и работает** (проверено по коду и тестам): создание трёх типов
ссылок, копирование, отзыв, вход хозяина в свою встречу, стук → одобрение →
отказ, кик гостя из звонка (с честной ошибкой, когда LiveKit кик не выполнил),
бейдж гостя на плитке и в шапке чата, «завершить временный чат» у хозяина,
самоуничтожение гостя, счётчик занятых мест.

**Чего не было — добавлено:**

| Что | Почему это дефект, а не «хотелка» |
|---|---|
| **Число мест** у создаваемой ссылки-встречи | Сервер принимает `max_uses` с v3; в интерфейсе не было ничего, и все ссылки всегда шли с серверным дефолтом |
| **«Тихий гость»** (`can_publish:false`) | Поле в БД, в API и в токене LiveKit есть с v3, UI — нет. Это единственная форма, в которой работает вебинар/демо |
| **«Отозвать все»** | Обещано концептом с v1 и не сделано: у кого утекла ссылка, тот жал «отозвать» по одной, на списке, который уезжает под курсором. `DELETE /api/guest-invites` |
| **Сколько ссылке осталось жить** | Ссылка на исходе выглядела точно так же, как свежая, хотя вся их суть — быть короткоживущими |
| **Значок «тихой» ссылки в списке** | Иначе разница видна только когда гость уже сидит в комнате и не может заговорить |
| **Звук стука у хозяина** | Карточка стука работает, только если хозяин смотрит в эту вкладку — а он обычно только что ушёл отправлять ссылку в другой мессенджер. У стука окно 5 минут, после чего человек за дверью просто уходит |

Детали, о которых стоит знать при доработке:

- «Отозвать все» закрывает вход **новым** гостям и **не прерывает** идущую
  встречу — так и написано в подтверждении; чтобы выгнать тех, кто уже внутри,
  нужен кик. Радиус действия ограничен своими ссылками (закреплено тестом:
  чужая живая ссылка обязана остаться живой).
- Звук стука звучит **даже когда окно в фокусе** (в отличие от звука сообщения):
  карточка может быть за пределами экрана на длинном списке чатов. Глушится
  общим переключателем звука чата. Файл `/sounds/<схема>/knock.mp3`
  опционален — по умолчанию синтезированный двойной сигнал, ни одного нового
  ассета в репозитории.
- Ручки гостевого контура переехали с чтения при импорте модуля на чтение
  **на запрос** (см. §3). Это поменяло семантику одного теста
  (`FEATURE_OPEN_REGISTRATION=0` теперь надо держать выставленной во время
  запроса, а не только в момент `buildApp()`) — тест обновлён вместе с
  объяснением.

**Локализация гостевых экранов — СДЕЛАНО.** `/guest/call/*`, `/guest/chat/*` и
общая карточка переведены на `t()` (60 новых ключей в обеих локалях). У гостя нет
аккаунта и настроек, поэтому язык берётся из браузера — **но только если в этом
браузере его ещё ни разу не выбирали**: чужой выбор не перетирается (закреплено
пятью тестами, включая «хранилище недоступно → ничего не трогаем»). Переключатель
EN/RU живёт на общей карточке, поэтому он в одном и том же углу на всех гостевых
экранах. Заодно из чата удалены дубли `CenterCard`/`Spinner` с комментарием
«такой же вид, как в /guest/call» — именно та форма, которая расходится.

**Агрегация стуков — СДЕЛАНО.** Больше трёх карточек на экране не бывает:
остальные сворачиваются в «и ещё N стучатся». До этого десятиместная встреча,
заполняющаяся разом, закрывала карточками весь интерфейс хозяина, причём
выдавливался наверх самый старый стук — тот, которому осталось меньше всего
времени.

**E2E против прод-харнесса — СДЕЛАНО.** `scripts/e2e-live/guest-v3-check.mjs`
прогнан по живому проду и **поймал регрессию от самой локализации**: харнесс
искал поле ника по русскому placeholder'у, а гостевые экраны теперь следуют
языку браузера — у Playwright это `en-US`, и шаг «войти во временный чат» падал
по таймауту. Починено с двух сторон: у гостевых полей появился `name`
(текстовый input без него — сам по себе странность), харнесс выбирает по нему,
а контекст браузера пинится на `ru-RU`, чтобы остальные селекторы по русским
подписям кнопок были детерминированы. Повторный прогон по проду — **14/14**
(в упавшем прогоне было 11/12: три последних проверки просто не дошли).

Побочное наблюдение оттуда же: в логе харнесса на каждой странице висит
`TypeError: Cannot read properties of undefined (reading 'waiting')`. Это
артефакт самого харнесса (`serviceWorkers: 'block'` — библиотека читает
`registration.waiting` у незарегистрированного воркера), а не дефект прода:
ошибка появляется и на обычных страницах приложения, которые прод отдаёт
неделями.

## 5. Стабильность и производительность

Смотрел то, что обычно и ломает такие сервисы: таймеры, фоновые задачи,
поведение при отказе зависимостей, индексы под горячие запросы.

**Хорошо, и это проверено, а не на веру:**

- Все девять `setInterval` на сервере либо `.unref()`, либо снимаются на
  `onClose`. Тик хартбита WS обёрнут в try/catch **на сокет**: один мёртвый
  сокет когда-то ронял весь тик и эскалировал в остановку процесса.
- `unhandledRejection` логируется и **не** роняет процесс, `uncaughtException` —
  роняет с дренажом. Разделение объяснено в коде и правильное.
- Рейт-лимитер живёт в Redis (счётчики переживают редеплой), fail-open по
  осознанному решению, ключ — user при живой сессии и IP иначе, что снимает
  коллизию всех за одним NAT.
- Горячие агрегаты подпёрты частичными индексами: `attachments_uploader_id_idx`
  и `attachments_lru_idx` — оба `WHERE evicted_at IS NULL`, ровно под
  квоту-на-пользователя и под порядок вытеснения. Сумма по всему пулу кэшируется
  на 30 с.

**Риски, которые остаются (не дефекты — то, за чем смотреть):**

1. **Свипер гостей молчал в проде пять дней** (`cb3d458`), и единственным следом
   была строка уровня 40, которую никто не читал. Урок «после деплоя грепать
   логи» держался на памяти человека. → **СДЕЛАНО**: `lib/log-counters.ts`
   вешается pino-хуком на каждый лог-вызов и считает warn/error за жизнь
   процесса, храня по одной усечённой строке контекста на уровень; счётчик виден
   в `/admin` → CONFIG. Здоровый инстанс стоит около нуля, а фоновая задача,
   падающая по таймеру, растёт так, что не заметить нельзя. Счётчик per-process
   и обнуляется рестартом — то есть показывает ровно окно «с момента деплоя».
2. **`GET /metrics` появился** — opt-in по `METRICS_TOKEN`, без него роут не
   регистрируется и путь отвечает 404 (неверный токен — тоже 404: ответ не
   должен подтверждать, что эндпоинт вообще есть). Намеренно узкий: сборка,
   аптайм, память, живые сокеты и тот самый счётчик warn/error. **Без
   per-user-серий** — скрейп не должен становиться способом узнать, кто сейчас
   онлайн, — и **без единого запроса в БД**: мониторинг не имеет права
   догружать базу ровно тогда, когда его спрашивают, почему база медленная.
   Сам Prometheus с Grafana всё ещё не подняты — это отдельный стек, и это
   записано в `docs/OPS.md`.
3. **Прод-образы работали на Node 20**, у которого EOL наступил в апреле
   2026-го, — то есть рантайм, который больше не получает патчей безопасности.
   Все четыре образа и контейнер предделойных тестов в `deploy.sh` переведены
   на `node:22-alpine` (тот же мажор, что в CI).
3. **Кэш настроек — 5 секунд на воркер.** Осознанно (см. §3), но это значит, что
   после изменения ручки два процесса до пяти секунд отвечают по-разному. Для
   этих ручек безвредно; для чего-то вроде «забанить» так делать нельзя.

## 6. Медиа

Пайплайн: presigned PUT/GET в MinIO/S3, шифрование на клиенте, учёт в
`attachments`, LRU-вытеснение по общему потолку + отдельная квота на
пользователя, отдельная чистка «сирот».

**Сильные места:** размер, заявленный клиентом, не считается истиной — при
следующем presign этого же пользователя размеры сверяются с реальным объектом
(`reconcileUploaderAttachmentSizes`); квота на пользователя — аддитивный слой
поверх глобальной, то есть один человек не может выесть общий пул; вытеснение
идёт «сначала сироты, потом давно не читанное» и опирается на индекс ровно этой
формы; строка не удаляется при вытеснении, а помечается — иначе клиент не смог
бы отличить «файла никогда не было» от «файл вытеснен, можно восстановить».

Проверено по коду, что закрыты два класса дыр, которыми такие пайплайны обычно и
текут: пересоздание presign на чужой ключ с подменённым `Content-Type` (иначе
чужой файл отдаётся как активный `text/html` с того же origin) и выдача
часового GET на картинку приватной группы тому, кого из группы уже удалили.

**Остаётся:** нет фонового «reconcile» размеров для пользователя, который
загрузил и больше не возвращался (сверка привязана к его же следующему presign);
Lite не имеет медиа-драйвера на локальной ФС (см. §2).

## 7. Безопасность

Периметр в очень приличном состоянии, и это результат прежних заходов
(закрытый бэклог на 118 находок, 28 находок ревью 13 августа, 30 правок обзора
сборок 14 августа), а не сегодняшнего дня.

Проверено предметно: `assertProdSecurityEnv` требует явные CORS-origin (без `*`)
и Redis в проде; `JWT_SECRET` короче 32 символов — фатальная ошибка старта;
`trustProxy` задан **числом хопов**, а не `true`, иначе клиент подделал бы
`X-Forwarded-For: 127.0.0.1` и вышел бы из-под всех лимитов через loopback-байпас
(байпас, к тому же, смотрит на адрес сокета, а не на `request.ip`); CSRF-защита
для «простых» запросов без preflight; deny-by-default гейт гостевой сессии;
`maxPayload` у WebSocket ограничен кратно прикладному лимиту; CSV-экспорт
экранирует формулы во **всех** колонках, потому что `user_agent` пишет атакующий.
`npm audit` чист и в прод-, и в dev-зависимостях.

**Про новое, что добавлено сегодня** (сам себе оппонент):

- Запись настроек — только `creator`, аудит на каждое изменение, значение
  зажимается в объявленный диапазон, неизвестный ключ → 404, чужой тип → 400.
- `ADMIN_BOOTSTRAP_USERNAME` **не создаёт** аккаунт и обезвреживается, как
  только создатель появился. Худший сценарий — оператор вписал чужой ник: это
  ровно та же степень доверия, что и `UPDATE` в psql, только без SSH.
- Ник для Lite проходит `assertSingleLine`, иначе перевод строки в GUI-визарде
  дописал бы в `.env.lite` произвольные переменные.
- Пинг Redis в `/admin/instance` ограничен по времени — иначе диагностическая
  ручка вешалась бы ровно в том случае, ради которого её открывают.

**Найдено при пуше и починено — самое серьёзное за весь заход.**

GitHub прислал пять открытых алертов Dependabot (три high), и все указывали на
**`client/package-lock.json`** — при том что корневой `npm audit` показывал 0.
Оба утверждения верны одновременно, и в этом вся суть:

`docker-compose.prod.yml` собирает `web` с `context: ./client` и
`client/Dockerfile`, который копирует **клиентский** лок и делает по нему
`npm ci`. Этот лок остался с тех пор, как репозиторий стал npm-workspace:
`npm install` внутри `client/` уходит вверх и правит КОРНЕВОЙ лок, а этот не
трогает никто. Он отставал молча — корневой резолвил nanoid 3.3.18, js-yaml
4.3.1, postcss 8.5.26, dompurify 3.4.14, а клиентский всё ещё пинил 3.3.16,
4.3.0, 8.5.22 и 3.4.12, и именно эти версии уезжали в образ, который отдаёт
приложение. Плюс `fast-uri` 3.1.4 (host confusion через обратный слэш), который
текущему дереву вообще не нужен.

Локальные тесты этого не видят по построению: они идут по корневому локу — где
патченые версии уже были и на них проходят 550 клиентских тестов. Ровно поэтому
дрейф и жил незамеченным.

Лок перегенерирован ВНЕ workspace (иначе npm перепишет корневой), пять пакетов
подняты до патченых, `fast-uri` выпал вместе с тремя сотнями babel-пакетов,
которых сборка давно не требует: 962 записи → 653. Проверено сборкой образа на
сервере ДО подмены контейнеров (`compose build web`, `npm ci` принял лок, «added
570 packages»), потом — в работающем контейнере (`nanoid 3.3.18`, `postcss
8.5.26`, остальные три в рантайм-образ вообще не попадают). GitHub закрыл все
пять алертов сам при следующем сканировании: **0 открытых**. **СДЕЛАНО**

**Починено здесь же:**

- **`SECURITY.md` дополнен** тремя разделами: гостевые ссылки (что именно
  сдерживает гостя каждого из двух типов и чего гостевой режим НЕ обещает —
  анонимности и E2EE против сервера на звонке), рантайм-настройки инстанса (кто
  может писать, что попадает в аудит, почему флаги фич остались в окружении) и
  **ротация ключей** — таблица «что меняем → чем платим», включая главное
  предупреждение: `TOTP_WRAP_KEY` ротировать на месте нельзя, иначе сохранённые
  TOTP-секреты перестают расшифровываться.
- Заодно исправлены два устаревших утверждения: «forward secrecy нет» (для 1:1
  она есть — Double Ratchet v2 + X3DH; её нет у групп с общим ключом сектора) и
  «JTI-денилист только в памяти» (он в Redis, а Redis в проде обязателен).
- **Подпись десктопных бандлов** — см. §9.

**Остаётся:** Windows Authenticode (см. §9).

**Что осталось**, по убыванию отдачи:

1. **Медиа-драйвер на локальной ФС для Lite** и **встроенный LiveKit** — оба в
   роадмапе и оба намеренно не тронуты здесь. Первый переписывает самый
   чувствительный путь (авторизация медиа сегодня держится на presigned-URL к
   S3), второй — стек звонков, который в этой среде нечем проверить, а
   выкатывать непроверенную звонковую инфраструктуру ровно то, от чего
   предостерегают правила проекта.
2. **Prometheus + Grafana как стек.** Эндпоинт есть, скрейпера нет.
3. **Windows Authenticode** — нужен сертификат и шаг импорта на раннере.
4. **iOS** — нужен Mac и решение владельца: добавлять таргет или убрать из
   планов совсем.
