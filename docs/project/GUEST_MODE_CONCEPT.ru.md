## 1. Что делаем (и что принципиально НЕ делаем)

Два механизма, оба доступны только **зарегистрированному** пользователю,
оба — через **ссылку с ограниченным числом мест** (v3: место = один гость;
временный чат всегда одноместный, встреча по умолчанию на 10 гостей):

1. **Гость на созвоне.** Пользователь создаёт ссылку на звонок
   (в существующем чате или отдельную комнату), отправляет её любым каналом.
   Гость открывает, вводит имя, «стучится». Пригласивший **лично одобряет** —
   гость попадает в звонок. Пригласивший может **кикнуть** в любой момент.
   **Аккаунт гостя не создаётся вообще** — после звонка остаётся только ник
   в истории (см. §3).

2. **Временный чат «с собой».** Пользователь создаёт одноместную ссылку на
   личный текстовый чат с собой. Гость входит по ссылке под временным именем,
   переписка E2EE. **Закрыл вкладку — назад пути нет** (ключ гостя живёт только
   в этой вкладке). Функционал гостя урезан до минимума: текст и выход.

**Жёсткий принцип:** без регистрации и без ссылки человек не может пользоваться
сервером **никак**. Никаких «открытых дверей», публичных комнат, гостевого
каталога. Ссылка = единственный вход, у неё конечное число мест, и каждого
гостя всё равно впускает человек.

## 2. Два механизма — потому что у них разная физика

Ключевое наблюдение из разведки кода: вся инфраструктура «жизни в системе»
(WS, доставка сообщений, блокировки, лимиты) адресуется по user id и членству
в `chat_members` — но **звонок через LiveKit из этого исключение**. SFU — это
отдельный сервер со своим токеном: identity в нём — произвольная строка
(`server/src/routes/call.ts:138-151`), и после выдачи токена участие в звонке
не касается ни Postgres, ни app-WS.

Отсюда два разных дизайна:

| | **A. Гость-на-созвоне** | **B. Временный чат** |
|---|---|---|
| Строка в `users` | **нет, никогда** | да, эфемерная (`user_group='guest'`) |
| Identity | `guest:<random>` только в LiveKit-токене | обычный user id |
| App-WS | не подключается вообще | подключается (нужен для сообщений) |
| Что использует | 3 публичных гостевых роута + LiveKit | стандартный пайплайн сообщений |
| Что остаётся после | ник в истории звонка (строка) | ничего (чат и гость удаляются) |
| Сдерживание | физическое: нет тела — нет доступа к API | deny-by-default hook (§6.3) |
| Зависимости | `FEATURE_CALLS` + настроенный LiveKit | ничего кроме ядра |

Механизм A — **сильнее исходного требования**: «аккаунт не сохраняется»
выполняется буквально, потому что аккаунт даже не создаётся. Гость звонка
физически не может дотянуться ни до одного API-роута с авторизацией: у него
нет ни cookie, ни users-строки, ни WS. Ревьюить нечего — нечему течь.

Цена A: гостевые звонки идут **только через LiveKit** (даже 1:1 — через SFU,
а не P2P-mesh). P2P-сигналинг требует app-WS, а app-WS требует users-строку
(`server/src/routes/ws.ts:62-125`) — «бестелесность» и P2P несовместимы.
На инсталляциях без LiveKit (минимальный Lite) гостевых звонков нет — честная
плата. E2EE-модель не ухудшается: ключ LiveKit-комнаты и сегодня выводится
сервером (`call.ts:190-192`, маркировка «не E2EE против сервера» —
`client/src/lib/livekit-call-manager.ts:9-14`), гость получает его тем же путём.

## 3. Механизм A — гость на созвоне

### 3.1. Создание ссылки

Из двух мест:
- **Из чата со звонком** — «Пригласить гостя в звонок»: ссылка привязана к
  `chat_id`, комната звонка = uuid чата (как сейчас: `call.ts:81-84`).
  Гость попадает **только в звонок** — не в чат: тела нет, историю, сообщения
  и список участников чата он не видит в принципе.
- **Отдельная комната** — «Быстрая встреча» (бывшая «быстрая связь» из v1,
  теперь это частный случай A): комната = свежий uuid без чата. Гость входит
  по ссылке; создатель — по странице `/meet/<room>` (`POST /api/call/token`
  авторизует владельца живой ссылки на эту комнату). Создание ссылки сразу
  уводит создателя в комнату, а из списка ссылок в неё можно вернуться —
  без этого автор «быстрой встречи» оставался снаружи собственной встречи.

Ссылка: `https://host/guest/call/<token>`, токен ≥128 бит. Свойства:
**с местами** (`max_uses`: 1 для чата, 10 по умолчанию для встречи; каждое
место расходуется одним одобрением), TTL
(по умолчанию 24 ч), отзывается создателем. Список своих активных ссылок —
в настройках, «Отозвать все» одним действием.

### 3.2. Стук и одобрение

До одобрения гость существует только в Redis — по образцу анонимного
rendezvous линковки устройств (`server/src/lib/device-rendezvous-store.ts`,
публичные роуты `server/src/routes/devices.ts:379,434`):

```
1. POST /api/guest/resolve { token }
     → { kind:'call', host_name, room_active: bool } | 404
   (единый 404 на несуществующий/истёкший/отозванный — enumeration guard,
    как дамми-ключ в auth: server/src/routes/auth.ts:71-76)

2. POST /api/guest/knock { token, nickname }
     → { knock_id, knock_secret, poll_interval_s }
   Redis knock:<id>, TTL 300 c. Ник ≤ 32 симв., не может совпадать с
   существующим username (регистронезависимо, через users_username_lower_unique)
   и с резерв-листом (server/src/lib/nickname.ts:7-18).

3. Пригласившему (и только ему): WS { type:'guest_knock', … } + push
   (sendPushToUser/sendNativePushToUser — server/src/lib/push.ts:105,161;
    новый type:'guest_knock' включить в isCallPayload push.ts:52-54, чтобы
    заголовок «Гость Имя стучится» не съела privacy-перезапись и FCM-канал
    был звонковым).

4. Гость поллит GET /api/guest/knock/:id?secret=… (2–3 c, максимум 5 мин).

5. POST /api/guest/knock/:id/approve  (auth: создатель ссылки)
   Атомарно: занимается ОДНО место ссылки (used_count+1; used_at ставится,
   когда ушло последнее) + в поллинг гостю уезжает:
     { livekit_url, livekit_token, call_e2ee_key }
   Токен: identity 'guest:<random>', name = ник, metadata {"guest":true,
   "invited_by":"<username>"}, canPublish/canSubscribe по ссылке,
   exp ≤ 2 ч. (Клеймов name/metadata сегодня нет вообще — call.ts:138-151;
   их добавление заодно чинит «участники SFU рендерятся как UUID» —
   client/src/lib/livekit-call-manager.ts:66-85, group-call-screen.tsx:495.)
   /deny — стук гаснет; ссылка НЕ сжигается, но создателю показывается
   кнопка «Отозвать ссылку» (на случай «утекла не тому»).
```

### 3.3. Кик и завершение

- **Кик**: `POST /api/guest-calls/:roomId/kick { identity }` — сервер минтит
  себе admin-токен (`roomAdmin:true`) и зовёт LiveKit RoomService
  `RemoveParticipant` (twirp HTTP на тот же хост, что `LIVEKIT_URL`; ключи
  уже есть). Identity дополнительно в Redis-денилист выдачи токенов — на
  случай не истёкшего гостевого JWT. Право кика: создатель ссылки; для
  чат-привязанного звонка — плюс admin/owner чата (решение §10.4).
- **Конец звонка**: комната пустеет → существующий webhook `room_finished`
  чистит ключ сессии (`call.ts:258-278`). Стандартный жизненный цикл.

### 3.4. Что остаётся

- Чат-привязанный звонок: в строку `call_sessions` (`schema.ts:1033-1051`)
  добавляем `guests jsonb` — `[{ nick, joined_at, left_at, kicked }]`.
  История звонка в чате показывает «+ гость Имя». Это и есть «сохраняется
  только ник».
- Отдельная комната: **ничего** (у `call_sessions.chat_id` NOT NULL, комнаты
  без чата не логируются). Для «резервного канала» отсутствие следов — фича.
- В `users`, `devices`, `chat_members` — ноль изменений и ноль строк.

### 3.5. UI гостя

`/guest/call/<token>` — публичная страница (в `PUBLIC_PREFIXES`,
`client/src/lib/public-routes.ts:29-39` — одно место закрывает все три
клиентских гейта). Экран: имя → «Постучаться» → ожидание → звонок
(динамический импорт livekit-client, как сейчас в
`client/src/lib/group-call-manager.ts:26-33`). Ни vault, ни WS, ни chatStore.
Плитка гостя у всех участников — с бейджем «гость» (из `metadata` токена).

## 4. Механизм B — временный чат «с собой»

### 4.1. Вход

```
Создатель: профиль/меню «+» → «Ссылка на временный чат» (TTL 24 ч, одноразовая)
Гость: /guest/chat/<token> → имя → [Войти]
  POST /api/guest/enter { token, nickname, public_key_jwk, ecdh_public_key_jwk }
  Атомарно: ссылка сжигается + создаются:
    users { username:'guest_<slug>', display_name:ник, user_group:'guest',
            guest_expires_at: now+12ч, guest_invited_by: создатель,
            is_discoverable:false, ключи из запроса }
    chat type='direct' + два chat_members (создатель, гость)
  → гость логинится своим эфемерным ключом через ОБЫЧНЫЙ /auth/challenge +
    /auth/verify (строка уже есть — ветка регистрации auth.ts:477-493 не
    задействуется; X-Client-Device-Id генерируется в sessionStorage,
    device-строку создаст upsertDeviceForSession как всем —
    server/src/lib/device-session.ts:26).
Создателю: WS 'guest_joined' + push «Гость Имя вошёл во временный чат».
```

Стука в чате **нет** (решение §10.2): ссылка одноразовая и личная — факт
владения ею и есть приглашение; защита от «утекла не тому» — мгновенное
уведомление создателю + кик + «Заблокировать».

Ключи гостя живут в `sessionStorage`: перезагрузку вкладки переживают,
закрытие вкладки — нет. «Закрыл — не вернёшься» обеспечено криптографией,
а не куками: подписать challenge больше нечем.

### 4.2. Ограниченный функционал

Гостю доступен **явный список** (всё остальное — 403, см. §6.3):

```
/api/auth/me | refresh | logout | ws-ticket        — жизнь сессии
/api/ws                                            — реалтайм
/api/chats/:id + /api/chats/:id/messages           — только свой чат
/api/messages/send | /api/messages/pending         — текст, E2EE fan-out
/api/users/:userId/devices                         — ТОЛЬКО со-участник чата
                                                     (ECDH для шифрования)
/api/guest/me/leave                                — выйти = самоуничтожиться
```

Ни медиа, ни стикеров/GIF, ни звонков (позвонить гостю → механизм A),
ни поиска людей, ни создания чатов/ссылок, ни профиля, ни vault/recovery/TOTP,
ни линковки устройств, ни push-подписок. Переписка — обычный per-device
fan-out E2EE (гость единственное устройство; чат создан пустым — истории до
гостя не существует, гейтить нечего). Rate-limit: `POST /api/messages/send`
берёт `max` по клейму `grp` проверенной сессии — гостю `GUEST_MSG_PER_MINUTE`
(дефолт 20), всем остальным неизменные 30/мин
(`server/src/routes/messages.ts` → `sendRateLimitMax`/`guestMsgPerMinute`),
ключ — user id самого гостя. Сверху — глобальный лимитер приложения 100/мин с
ключом `user:<id>` (`server/src/app.ts:292-348`).

### 4.3. Смерть гостя

Что случится раньше:
- **«Выйти»** → `POST /api/guest/me/leave` — немедленный purge;
- **создатель**: «Завершить чат» / кик / блок → purge;
- **вкладка закрыта**: ключ утерян; сервер добивает по неактивности —
  sweeper: `user_group='guest'` и не онлайн и `last_seen_at < now - 60 мин`
  (онлайн-статус уже есть: `areOnline` — `server/src/ws/registry.ts:421-449`);
- **жёсткий предел** `guest_expires_at` (12 ч) — refresh сессии за него
  не продлевает.

Purge переиспользует `server/src/lib/admin-purge-user.ts`: devices умирают
каскадом → все сессии мертвы через существующую проверку живой device-строки
(`server/src/lib/auth-user.ts:150-157`) + Redis fast-path. **Вместе с гостем
удаляется и сам временный чат** (со всеми ciphertext-строками, решение §10.3) —
«временный» значит временный; у создателя остаётся только то, что его клиент
уже расшифровал локально.

## 5. Модель данных (v2 — заметно меньше v1)

```sql
-- Общая таблица одноразовых ссылок (оба механизма)
CREATE TABLE guest_invites (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  token       text NOT NULL UNIQUE,          -- ≥128 бит, base64url
  purpose     text NOT NULL,                 -- 'call' | 'chat'
  created_by  uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  chat_id     uuid REFERENCES chats(id) ON DELETE CASCADE,  -- call-в-чате
  room_id     uuid,                          -- standalone-комната (call)
  expires_at  timestamptz NOT NULL,          -- TTL до первого входа
  max_uses    integer NOT NULL DEFAULT 1,    -- места (1 = одноразовая)
  used_count  integer NOT NULL DEFAULT 0,    -- занято мест
  used_at     timestamptz,                   -- стоит, когда мест не осталось
  revoked_at  timestamptz,
  can_publish boolean NOT NULL DEFAULT true, -- «тихий гость» для демо
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- Только для механизма B
ALTER TYPE user_group ADD VALUE 'guest';                    -- schema.ts:62-68
ALTER TABLE users ADD COLUMN guest_expires_at timestamptz;  -- NULL = не гость
ALTER TABLE users ADD COLUMN guest_invited_by uuid
  REFERENCES users(id) ON DELETE SET NULL;

-- Только для истории механизма A (чат-привязанные звонки)
ALTER TABLE call_sessions ADD COLUMN guests jsonb;          -- [{nick,…}]
```

Ушло по сравнению с v1: роль `guest` в `chat_member_role` (B-чат — direct,
истории до гостя нет → гейт `joined_at` не нужен), `chats.expires_at`
(standalone-комнаты — не чаты), политика `allow_media` (text-only жёстко).
`max_uses` вернулся в v3 — встреча на одного гостя встречей не является.
Стук — только Redis, в БД не попадает.

## 6. Сдерживание и периметр

### 6.1. Новая публичная поверхность — пять роутов

`resolve`, `knock`, `knock/:id` (поллинг), `knock/:id/cancel`, `enter` + две
публичные страницы `/guest/call/*`, `/guest/chat/*`. Регистрируются **только**
при `FEATURE_GUESTS` (паттерн отключаемых групп роутов, выключено = 404).

Rate-limit — не «5/15 мин на всё», как задумывалось по образцу auth-скоупа:
такой бюджет считает гостей поштучно, а они сидят за одним адресом целыми
переговорками, и шестой гость десятиместной встречи вылетал на четверть часа
с живой ссылкой в руках. Бюджеты рассчитаны **на встречу**, тремя корзинами
(значения — §6.4), и висят на общем лимитере через per-route
`config.rateLimit`: своя `register(rateLimit, …)` подняла бы свежий
in-process LocalStore, и счётчики умирали бы на каждом пересборе api.

Лимит — не то, что защищает ссылку (32 случайных символа, места в Postgres,
`GUEST_MAX_ACTIVE` на живых гостях), а защита от флуда.

### 6.2. Сессии

Гость A аутентифицируется **только в LiveKit** (JWT ≤ 2 ч) — `fm_session` у
него не появляется вовсе. Гость B получает `fm_session` с клеймом
`grp:'guest'` — именно клеймом, **не** `scope`: любой токен со `scope`
отвергается как сессия (`server/src/lib/auth-user.ts:62-64`). TTL —
`min(12 ч, guest_expires_at − now)`; `/auth/refresh` (`auth.ts:180`) переносит
клейм и не выходит за предел.

### 6.3. Deny-by-default для B

На сервере нет глобального auth-hook (авторизация по-роутовая), поэтому
добавляется один `onRequest`-hook в `app.ts`: JWT несёт `grp:'guest'` и
`request.routeOptions.url` не в `GUEST_ALLOWED_ROUTES` (список §4.2) →
`403 GUEST_FORBIDDEN`. Дёшево (по клейму, без БД), authoritative-проверка
`userGroup` в хендлерах — второй пояс. Любой будущий роут закрыт для гостей
по умолчанию, пока его руками не внесли в список.

### 6.4. Ручки (env, с дефолтами)

Реализованные ручки (сверено с кодом; операторская версия — DEPLOY(.ru).md):

| Ручка | Дефолт | Что |
|---|---|---|

| `GUEST_MEETING_SEATS` | 10 | мест на новой ссылке-встрече, зажато в 1…50 (у B-ссылки всегда 1) |
| `GUEST_CHAT_TTL_HOURS` | 12 | жёсткий предел жизни B-гостя |

| `GUEST_OFFLINE_GRACE_MIN` | 60 | офлайн до purge B-гостя |
| `GUEST_SWEEP_INTERVAL_MS` | 300000 | период sweeper'а |
| `GUEST_MAX_LINKS_PER_USER` | 20 | активных ссылок на пользователя |
| `GUEST_MAX_ACTIVE` | 50 | одновременных гостей на сервер (A+B) |
| `GUEST_MSG_PER_MINUTE` | 20 | `POST /messages/send` от B-гостя (у прочих — 30) |

Отдельной `GUEST_CALL_TOKEN_TTL_HOURS` из ранних редакций этого документа
**нет**: LiveKit-JWT гостя минтится общим `LIVEKIT_TOKEN_TTL_SECONDS`
(дефолт 2 ч, зажат в 5 мин…4 ч — `resolveCallTokenTtlSeconds` в
`server/src/routes/call.ts`), тем же, что у обычного участника.

### 6.5. Прод-периметр

Edge (Caddy + Anubis + CrowdSec) живёт вне репозитория (`Caddyfile:1-3` →
`~/infra/caddy/sites/onetothree.ru.caddy`): при включении фичи провести
`/guest/*` и `/api/guest/*` явно. Anubis PoW перед гостевыми страницами —
желанный бесплатный анти-бот; CrowdSec-сценарий «много knock/enter с IP».

## 7. Честность (что обещаем и чего не обещаем)

- **A-гость и E2EE.** LiveKit-путь и сегодня «не E2EE против сервера»
  (ключ комнаты серверный) — гость модель угроз не меняет. В UI гостевого
  звонка — та же честная пометка, что у групповых.
- **B-гость и E2EE.** Настоящий per-device fan-out: сервер видит ciphertext.
  Но личность гостя **не верифицирована по определению** — бейдж «гость»
  обязателен везде (шапка чата, плитка звонка, история). Safety numbers для
  гостя не показываем — нечего подтверждать.
- **Метаданные.** Сервер видит IP/UA гостя (B: `devices.ip_address`; A: логи
  edge). Гостевой режим — про отсутствие трения, не про анонимность.
- **Сообщения.** «Удаление временного чата» удаляет серверные ciphertext-копии
  и UI; то, что клиент создателя уже расшифровал и закэшировал локально,
  остаётся у него (как у любого собеседника в любом E2EE-мессенджере).
- **Открытая регистрация.** Сегодня она невыключаемая (ветка регистрации в
  `auth.ts` безусловна; `REGISTRATION_ENABLED` не существует). Гостевые ссылки
  становятся «единственной дверью для чужих» только вместе с флагом
  `FEATURE_OPEN_REGISTRATION` (default on — поведение не меняется;
  рекомендация приватным серверам: off). Маленькая смежная задача Phase 0.

## 8. Угрозы → меры

| Угроза | Мера |
|---|---|
| Перебор токенов | ≥128 бит; scoped rate-limit; единый 404; Anubis PoW |
| Ссылку переслали не тому | одноразовость; A — личный апрув создателя; B — мгновенное уведомление + кик/блок; отзыв ссылки |
| Имперсонация ником | ник ≠ существующий username (case-insensitive) + резерв-лист; вечный бейдж «гость»; в A ник зашит в токен (`name`), сменить нельзя |
| Спам/флуд B-гостя | text-only; `GUEST_MSG_PER_MINUTE` на `POST /messages/send` по клейму `grp:'guest'` (`server/src/routes/messages.ts` → `sendRateLimitMax`); сверху глобальный лимитер `server/src/app.ts:292-348`; кик/блок; `user_blocks` работает штатно |
| B-гость лезет в чужие API | deny-by-default hook — один код-путь на ревью |
| A-гость лезет куда-либо | не может физически: нет ни cookie, ни users-строки, ни WS |
| «Вечный гость» | A: JWT ≤ 2 ч, комната умирает; B: TTL 12 ч + офлайн-grace + sweeper |
| DoS стуками/поллингом | TTL стука 5 мин; per-IP/пер-токен лимиты; poll_interval подсказывается сервером |
| Накопление мусорных ссылок | TTL обязателен; `GUEST_MAX_LINKS_PER_USER`; список «мои ссылки» + «Отозвать все»; sweeper чистит истёкшие |
| Злоупотребление своими юзерами | ссылки может создавать любой зарегистрированный, но: лимиты выше, `guest_invited_by`/`created_by` — всегда известно, кто впустил; админ видит и может выключить фичу целиком |

## 9. План

### Phase 0 — фундамент (мал)
- `FEATURE_GUESTS` (**default off** — девиация от «ON-если-не-выключен»,
  `server/src/lib/feature-flags.ts:17-22`; задокументировать) + capability
  `guests:false` в клиентском дефолте (`client/src/lib/api/capabilities.ts:26-35`)
  + чекбокс Lite.
- `FEATURE_OPEN_REGISTRATION` (default on).
- Таблица `guest_invites` + sweeper-интервал (первый фоновый чистильщик в
  проекте): истёкшие ссылки, позже — гости B.

### Phase 1 — механизм A: гость на созвоне
Ноль миграций в `users`/`chats` — самый безопасный старт.
- Роуты: create/list/revoke ссылок; `resolve`/`knock`/поллинг (Redis-store по
  образцу device-rendezvous); `approve`/`deny`; `kick` (LiveKit RemoveParticipant).
- LiveKit-токен: ветка выдачи для `guest:<id>` + клеймы `name`/`metadata`
  для ВСЕХ участников (заодно чинит UUID-имена в SFU).
- Push `guest_knock` (+ фикс смежного бага: push первого участника групзвонка
  уходит `type:'message'` в тихий канал — `server/src/routes/ws.ts:1205`).
- Клиент: `/guest/call/[token]` (+ `public-routes.ts`), экран стука, гостевой
  звонок; карточка стука в UI звонка создателя; «Быстрая встреча» (standalone).
- `call_sessions.guests` — ник в истории.

### Phase 2 — механизм B: временный чат
- Миграция `users` (enum + 2 колонки), `enter`, deny-by-default hook + тесты
  «гостю 403 на всё, кроме списка», purge-цепочка (leave/кик/офлайн/TTL),
  минимальный чат-шелл гостя, бейджи, уведомление создателю.

### Phase 3 — полировка
- Прод-edge чеклист в DEPLOY (`/guest/*` в Caddy/Anubis/CrowdSec). ✅
- «Тихий гость» (`can_publish:false`) — сервер умел с v3, **чекбокс в модалке
  ссылок появился 2026-08-20**; в списке ссылок такая ссылка помечена значком
  перечёркнутого микрофона. ✅
- Число мест у создаваемой ссылки-встречи задаётся в той же модалке (пусто =
  серверный дефолт `guest_meeting_seats`). ✅
- **«Отозвать все»** — `DELETE /api/guest-invites` + кнопка над списком.
  Отзыв закрывает вход НОВЫМ гостям; уже идущую встречу он не прерывает
  (для этого — кик). ✅
- В списке ссылок видно, сколько ссылке осталось жить. ✅
- Звук стука у хозяина (`playKnockSound`, `/sounds/<схема>/knock.mp3`
  опционален — по умолчанию синтезированный двойной сигнал; глушится общим
  переключателем звука чата). ✅
- Ручки `guest_link_ttl_hours` / `guest_meeting_seats` / `guest_chat_ttl_hours` /
  `guest_max_links_per_user` / `guest_max_active` читаются **на каждый запрос**
  через настройки инстанса и меняются из `/admin` → CONFIG без рестарта. ✅
- **Локализация гостевых экранов** (2026-08-20). `/guest/call/*`,
  `/guest/chat/*` и общий экран комнаты переведены на `t()`; у гостя нет
  аккаунта и настроек, поэтому язык берётся из браузера — **только если в этом
  браузере язык ещё ни разу не выбирали** (чужой выбор не перетирается), а
  переключатель EN/RU висит в одном и том же углу карточки на всех гостевых
  экранах. Дубли `CenterCard`/`Spinner` в чате удалены — теперь общий компонент.
  ✅
- **Агрегация стуков** ✅ — на экране максимум три карточки (самые старые, они
  же ближе всех к истечению), остальные свёрнуты в строку «и ещё N стучатся».
  Десятиместная встреча больше не закрывает карточками весь интерфейс хозяина.
- Остаётся: e2e-тесты обоих потоков против прод-харнесса.

Порядок 0 → 1 → 2 намеренный: A даёт ценность без единого изменения в моделях
аккаунтов; B включает всё «тяжёлое» (deny-hook, purge) вторым шагом.

### Не делаем (v2)
- Гостей в **группах** и групповых чатах — выкинуто из v1 решением владельца.
- Многоразовые гостевые ссылки, гостевой каталог, «стук кому угодно».
- Апгрейд «гость → аккаунт» — противоречит «аккаунт не сохраняется»; захочет —
  зарегистрируется как все.
- Сохранение/восстановление гостевых сессий; медиа у гостей; P2P у A-гостей.

## 10. Решения владельца (зафиксированы 2026-08-12)

1. **Порядок фаз**: A (созвон) первым, B (чат) вторым — ноль миграций на старте.
2. **Вход в B-чат**: сразу по ссылке, без стука. Контроль — уведомление
   создателю + кик/блок + одноразовость ссылки.
3. **Судьба B-чата**: после смерти гостя удаляется целиком, включая серверные
   ciphertext-копии. Read-only архива нет.
4. **Кик A-гостя из звонка в существующем чате**: пригласивший **и**
   admin/owner чата.
5. **TTL непринятой ссылки**: 24 ч по умолчанию (ручка `GUEST_LINK_TTL_HOURS`).
